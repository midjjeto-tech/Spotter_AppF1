# Team Radio в стиле F1 Manager — план реализации

**Дата:** 2026-07-29
**Аудит:** `docs/superpowers/specs/2026-07-29-f1-manager-radio-redesign.md`
**Проверочные команды:** `py -3.12 -u -m pytest -q` · в `NewSpotterUI`:
`pnpm exec tsc --noEmit`, `pnpm build`, затем синхронизация `out → webui/`.

Каждая задача завершается зелёными тестами и может быть остановлена без поломки
приложения. `CONTEXT.md` обновляется после задач 2, 4, 6, 8 (правило «каждые 2»).

## Ключевые проектные решения

Приняты по итогам аудита; здесь, чтобы не перерешать их в каждой задаче.

**Где живёт доменная модель.** Новый пакет `core/radio/` — `message.py`
(`RadioMessage`), `policy.py` (urgency/TTL/interrupt/канал по коду),
`situations.py` (`situation_id`), `session.py` (активное сообщение + история).
Не в `core/engine.py` (уже ~4000 строк) и не в `core/commentary_events.py`:
`CommentaryEvent` — это вход (телеметрия → событие), `RadioMessage` — выход
(событие → речь). Смешивать два направления в одном типе значит заставить его
делать две работы.

**Где строится сообщение.** В `_commentary_loop`, сразу после получения текста
(сегодня engine.py:2756-2787) и **до** паузы `MIN_COMMENT_GAP`. Всё, что ниже
по потоку, работает с `RadioMessage`, а не с dict-событием.

**Совместимость каналов.** Существующий `commentator/channel_router.py`
(`commentary`/`radio`/`overlay`) — это *способ доставки*, он остаётся как есть.
Новый `channel` (`spotter`/`engineer`/`commentator`) — это *кто говорит*, новая
ортогональная ось. Поле `feed[].channel` не меняет значения; новый канал едет
отдельным полем.

**Срочность.** `urgency` выводится один раз в `core/radio/policy.py`:
`priority == "critical"` → `critical`; иначе таблица по `event_code`; иначе по
importance (≥80 high, ≥50 normal, иначе low). Порядок именно такой — таблица
кодов должна уметь поднять погоду/SC до `high`, даже если importance их не
дотянул.

**Позднее связывание.** `_resolve_volatile_phrase` переносится с точки «после
получения текста» на точку «перед синтезом» внутри пути воспроизведения.
Механизм тот же (`resolve_volatile`), меняется только момент вызова.

**Что не откроем заново.** `TTSQueue` critical-прерывание, `_stream_lock`,
`radio_fx` на воспроизведении, `TTSCache.version`, `SituationDedup`,
`SessionGuard`, fanout в RaceFeed — расширяем, не дублируем (аудит §9).

## Task 2 — Доменная модель и очередь

**Цель:** `RadioMessage` существует, несёт канал/срочность/TTL/политику/ID и
проходит через `_commentary_loop` без изменения слышимого поведения.

**Файлы:**
- `core/radio/__init__.py`, `message.py`, `policy.py`, `situations.py` — новые
- `core/commentary_events.py` — добавить `created_at` рядом с `enqueued_at`
  (не переименовывать: `is_stale_backlog_event` читает `enqueued_at`)
- `core/engine.py::_commentary_loop` — построить `RadioMessage`, дальше по нему

**Шаги (TDD):**
1. `RadioMessage` (frozen dataclass): `id`, `event_code`, `channel`, `category`,
   `urgency`, `speaker`, `phrase`, `created_at`, `expires_at`,
   `interrupt_policy`, `dedupe_key`, `situation_id`, `source_snapshot`,
   `volatile_fields`, `ui_title`, `ui_summary`, `state`. Тест: неизменяемость,
   сериализуемость в JSON-safe dict.
2. `policy.channel_for(event)` — `SPOTTER_*` → spotter; `SPEAKER_ENGINEER` или
   код из инженерного набора (§2 аудита) → engineer; иначе commentator. Тест:
   таблица кодов из аудита целиком.
3. `policy.urgency_for(event)` — порядок critical → таблица → importance.
   Тест: `SPOTTER_*` critical, `SAFETY_CAR_DEPLOYED` high, `AMBIENT` low.
4. `policy.ttl_for(code)` — значения из ТЗ §7 как именованные константы.
   `expires_at = created_at + ttl`. Тест: spotter 1–2 с, погода 20–40 с,
   у critical box-call TTL не меньше 8 с.
5. `policy.interrupt_policy_for(urgency, code)` → interrupt / next / replace /
   drop_if_busy. Тест: critical → interrupt; ENGINEER_GAP_DIGEST → replace.
6. `situations.situation_id(event, telemetry)` — расширяет, а не заменяет
   `SituationDedup`: формат `damage:front_wing:lap_12`, `box_call:window_2`,
   `weather:rain_front_1`, `battle:norris:lap_18`, `spotter:right:vehicle_7`.
   Тест: повторная телеметрия даёт тот же id; смена соперника/круга — новый.
7. Встроить в `_commentary_loop`: сообщение строится, логируется, но решения
   принимает прежний код. Тест: полный набор существующих тестов зелёный.

**Проверка:** `pytest -q` зелёный; новых слышимых изменений нет.
**После Task 2 — обновить `CONTEXT.md`.**

## Task 3 — Engineer phrase bank

**Цель:** инженерские фразы собраны в одном месте, с вариантами по срочности и
проверяемыми ограничениями.

**Файлы:**
- `commentator/engineer_phrases.py` — новый
- `core/strategy_ai/*.py` — трекеры отдают ключ+аргументы либо берут строку из
  банка (строки не остаются в двух местах)
- `commentator/brain.py` — guardrails для LLM

**Шаги:**
1. Банк: `PHRASES[category][urgency] -> tuple[str, ...]`, 4–8 вариантов на
   ситуацию. Стиль по ТЗ §10 (команда → причина, число ближе к началу).
2. Тесты ограничений длины: spotter 1–5 слов, critical 3–9, high 5–14,
   normal 7–18, PTT ≤ 2 предложения.
3. Тест на запрещённые плейсхолдеры: ни одна фраза не содержит незакрытых
   `{...}`, `None`, `—` в позиции числа.
4. Тест TTS-безопасности: пунктуация из уже принятого набора, числа проходят
   `core/num_to_words.py`.
5. Guardrail LLM: список полей, которые модель не может менять (box-call,
   сторона, тип флага, тип повреждения, compound, числа, штраф, требуемое
   действие). Тест: попытка сгенерировать critical через LLM — отказ, берётся
   банк.
6. Перенос строк из трекеров в банк по одному, с прогоном тестов трекера после
   каждого. `_LEFT_ENTER`/`_BOTH`/`_CLEAR` из `spotter.py` мигрируют вместе с
   кодом-детектором в `engine.py:1292-1299`, который сравнивает фразу со
   списком — эту связку нужно заменить на явный код от трекера.

**Проверка:** `pytest -q`; выборочное чтение сгенерированных фраз глазами
(memory: зелёные тесты пропускали несклоняемые имена).

## Task 4 — Volatile telemetry и актуальность

**Цель:** устаревшее число не произносится; проверка идёт максимально близко к
звуку.

**Файлы:**
- `core/engine.py` — перенос точки вызова `_resolve_volatile_phrase`
- `voice/tts.py` — хук ре-валидации перед синтезом и перед воспроизведением
- `core/radio/policy.py` — правила «что делать, если данных нет»

**Шаги:**
1. Расширить `resolve_volatile` токенами: `{gap_clause}`, `{position_clause}`,
   `{fuel_clause}`, `{tyre_clause}`, `{ers_clause}` (уже есть). Тест на каждый:
   нет данных → клауза удаляется целиком, остальная фраза остаётся.
2. Тест «сообщение теряет смысл без числа» → отменяется целиком, а не
   произносится обрубком.
3. Перенести вызов резолвера: из `_commentary_loop` (сегодня engine.py:2758) в
   колбэк, который `Voice` вызывает перед синтезом. Тест: собрано при 60%,
   озвучено при 14% — звучит 14% (сценарий уже есть в
   `tests/test_engine_planner.py`, расширить на новую точку).
4. Ре-валидация перед воспроизведением: `expires_at` прошёл / ситуация закрыта
   / заменено более новым / уже озвучено другим кодом → отмена с состоянием
   `cancelled` и отметкой в истории. Тест на каждый из четырёх случаев.
5. Никогда не произносить `—`, `None`, отрицательный gap, процент вне 0–100.
   Тест-барьер на финальной строке перед синтезом.

**Проверка:** `pytest -q`.
**После Task 4 — обновить `CONTEXT.md`.**

## Task 5 — PTT-диалог, история радио и UI projection

**Цель:** бэкенд отдаёт полное состояние радио; «повтори» работает; состояния
сообщений видимы.

**Файлы:**
- `core/radio/session.py` — активное сообщение + кольцевая история
- `core/ui_state.py` — секция `radio` в проекции
- `core/engine.py` — фикс `set_speaking` (находка §6 аудита)
- `commentator/radio_answer.py` — новые темы и команды
- `web_server.py` — при необходимости отдельный роут истории

**Шаги:**
1. **Фикс `speaking`:** состояние ставится при старте реального воспроизведения
   и снимается при завершении/прерывании, а не вокруг мгновенного `say()`.
   Тест: `speaking` остаётся True всё время работы `_play_blocking`.
2. Состояния сообщения: `queued` → `synthesizing` → `playing` →
   `completed` / `cancelled` / `interrupted`. Тест на каждый переход.
3. `last_completed_engineer_message` — отдельно от последнего события, от текста
   комментатора, от прерванного и от отменённого. Тест: «повтори» после
   прерывания повторяет предыдущее *завершённое*, не прерванное.
4. Команда «повтори» в `_COMMAND_STEMS`. Тесты на стемы.
5. Недостающие темы Q&A по ТЗ §12 относительно текущих 13: состояние переднего
   крыла, состояние машины целиком, активная стратегия, Safety Car/VSC,
   последний круг/сектор, текущий соперник, «тише», «говори чаще». Тест на
   каждую тему + на «Данных нет» при отсутствии данных.
6. Секция `radio` в `/api/state`: `status`, `active_message`, `history`
   (ограниченная), `settings`, `ptt`. Существующие `speaking`/`now_speaking`/
   `radio_message`/`voice_query` **остаются** (их читают dashboard и оверлей).
   Тесты: сериализуемость, отсутствие удержания lock'ов, лимит истории,
   стабильные ID.
7. Радио-сеанс: PTT-цикл (listening → распознано → checking data → ответ →
   история → компактный idle) отражён в `ptt`-подсекции. Автоматические
   сообщения попадают в историю без фиктивной реплики пилота.

**Проверка:** `pytest -q`.

**Шаги:**

   существующей `RADIO_TEXT_TTL_S`.
5. Waveform только во время записи/воспроизведения; анимации на transform/opacity.
6. Сохранить draggable layout, click-through и edit mode без изменений.

**Проверка:** `tsc --noEmit`, `pnpm build`, синхронизация; визуальный прогон

## Что нельзя подтвердить автоматическими тестами

Требует реальной гонки F1 25: калибровка TTL спотера, ощущение каданса
инженера, слышимость прерывания без щелчка, поведение overlay в
borderless/windowed, реальная частота ситуаций для дедупа.
