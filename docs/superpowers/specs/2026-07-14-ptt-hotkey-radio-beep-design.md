# Глобальный хоткей push-to-talk + звук-маркер «слушаю» — Design Spec

**Дата:** 2026-07-14
**Статус:** утверждён, готов к плану реализации
**Источник:** запрос пользователя — сейчас, чтобы задать вопрос AI, нужно свернуть
игру и кликнуть кнопку «Спросить» в UI; хочется бинд, как в самой игре (не отвлекаясь
от гонки), плюс характерный радио-щелчок как маркер «AI начал слушать».

## 1. Обзор

Push-to-talk уже реализован полностью (`core/engine.py::ask_voice_question()` →
`_run_voice_question()`: запись → STT → `commentator/radio_answer.py` → голосовой
ответ), запускается кликом по кнопке-микрофону в топбаре (`NewSpotterUI/components/
spotter/topbar.tsx`). Глобальные хоткеи, работающие пока F1 25 в фокусе (без
переключения окна), тоже уже есть — `core/hotkeys.py::GlobalHotkeyManager`, Win32
`RegisterHotKey`, 5 фиксированных нерегулируемых комбинаций (Ctrl+Alt+C/P/T/X/S).

Эта фича добавляет: (1) 6-ю, пользовательски настраиваемую комбинацию, которая
дёргает тот же `ask_voice_question()`; (2) короткий звук-маркер начала прослушки,
переиспользуя уже существующий синтез радио-щелчка (`voice/radio_fx.py::squelch()`).

## 2. Решения пользователя

1. **Комбинацию клавиш выбирает сам пользователь** (не фиксированный дефолт от
   разработчика) — единственная настраиваемая горячая клавиша в приложении на
   сегодняшний день.
2. **Поведение записи — как сейчас у кнопки «Спросить»**: нажал — идёт запись
   фиксированной длины (`config.VOICE_QUESTION_MAX_SEC`), сама останавливается и
   распознаёт. Настоящий hold-to-talk (зажал/отпустил) — явно отклонён, не в
   скоупе (потребовал бы отдельного механизма отслеживания key-up, которого
   `RegisterHotKey` не даёт).
3. **Смена бинда применяется после перезапуска Spotter App** — не в живую. Явный
   компромисс, принятый пользователем: живая перерегистрация потребовала бы
   отдельного протокола сообщений в Win32-потоке хоткеев ради второстепенного
   UX-удобства.

## 3. Цели и не-цели

**Цели**
- Настраиваемый глобальный хоткей push-to-talk, работает без переключения окна.
- Короткий радио-щелчок сразу при срабатывании (хоткей ИЛИ клик в UI — единая
  точка воспроизведения, не дублировать логику), прерывающий то, что сейчас
  звучит (как реальная рация: входящая передача обрывает прежнюю).
- Валидация бинда: минимум один модификатор (Ctrl/Alt/Shift) + разрешённая
  клавиша (A-Z, 0-9, F1-F12), без коллизии с уже занятыми Ctrl+Alt+C/P/T/X/S.

**Не-цели (YAGNI)**
- Hold-to-talk (пункт 2 выше).
- Живая перерегистрация без перезапуска (пункт 3 выше).
- Настраиваемость СУЩЕСТВУЮЩИХ 5 хоткеев — вне скоупа, остаются фиксированными.
- Отдельный звуковой ассет — переиспользуем существующий синтетический squelch,
  новый .wav-файл не нужен.

## 4. Архитектура

```
[Hotkeys view, NewSpotterUI] — новая строка «Спросить голосом (push-to-talk)»
  ├─ KeyCap×N (как остальные 5 строк) + кнопка «Записать»
  ├─ клик «Записать» → следующий keydown с ≥1 модификатором и разрешённой
  │    клавишей захватывается, валидируется на клиенте (не совпадает с занятыми)
  └─ POST /api/settings {ptt_hotkey: {ctrl, alt, shift, key}} → saveSettings()
       (уже существующий эндпоинт/функция, ничего нового на бэкенде для сохранения)

[core/hotkeys.py::GlobalHotkeyManager] — при старте потока (_loop):
  регистрирует 5 фиксированных + 6-ю из self._settings.get("ptt_hotkey")
  (если задан и валиден) → dispatch(6) → engine.ask_voice_question()

[core/engine.py::_run_voice_question()] — ДО self._voice_listener.record(...):
  self.voice.play_beep()   # единая точка для хоткея И кнопки UI

[voice/tts.py::Voice.play_beep()]
  1. self._interrupt_playback()           # глушит текущую фразу
  2. squelch = radio_fx.squelch(sr)       # переиспользуем существующий синтез
  3. воспроизводит через ОТДЕЛЬНЫЙ sd.OutputStream, close()/abort() строго
     под self._stream_lock — тот же паттерн, что только что закрыл крах
     ucrtbase.dll (см. _play_wav) — НЕ повторять старую гонку.
```

### 4.1 `core/settings.py`
Новый ключ в `DEFAULTS`:
```python
"ptt_hotkey": {"ctrl": True, "alt": True, "shift": False, "key": "V"},
```

### 4.2 `core/hotkeys.py`
- `_vk_from_settings(hk: dict) -> tuple[int, int] | None` — конвертирует
  `{"ctrl","alt","shift","key"}` в `(mods, vk)` для `RegisterHotKey`. Разрешённые
  `key`: `A-Z`, `0-9`, `F1`-`F12` (иначе `None` — не регистрируем, лог warning,
  fail-safe как остальной хоткей-стек). Требует ≥1 модификатор — иначе `None`.
- `GlobalHotkeyManager._loop()`: после регистрации 5 фиксированных — читает
  `self._settings.get("ptt_hotkey")`, конвертирует, если валиден и НЕ совпадает
  с (mods, vk) любого из 5 фиксированных — регистрирует под id=6, добавляет в
  `registered` (для корректного `UnregisterHotKey` при остановке).
- `_dispatch()`: `6: self._push_to_talk`.
- `_push_to_talk(self) -> None`: `self._engine.ask_voice_question()` — тот же
  метод, что вызывает `POST /api/voice/ask` от кнопки в топбаре; полностью
  переиспользует существующий busy-гейтинг (`is_critical_active`, `in_progress`).

### 4.3 `voice/tts.py`
Новый метод `Voice.play_beep(self) -> None`:
```python
def play_beep(self) -> None:
    """Короткий рут-сквелч — маркер «AI начал слушать» (push-to-talk).
    Сначала глушит текущую фразу (_interrupt_playback — как реальная рация:
    входящая передача обрывает прежнюю), затем играет squelch через отдельный
    sd.OutputStream. close()/abort() — строго под self._stream_lock (см.
    _play_wav) — та же дисциплина, что закрыла access violation в ucrtbase.dll,
    повторно эту гонку не открывать."""
```
- Не через `TTSQueue` (не текст, не нужен кэш/приоритет очереди) — прямой,
  блокирующий вызов на текущем потоке (вызывается из фонового потока
  `_run_voice_question`, не из UI-потока — блокировать нечего).
- `radio_fx.squelch(sr)` — тот же вызов, что уже используется для обрамления
  фраз при включённом radio-эффекте; параметры по умолчанию (`ms=70, level=0.16`)
  сохраняем без изменений — не отдельный «дизайн звука», а переиспользование
  существующего.
- Любая ошибка (`sounddevice`/`numpy` недоступны, устройство занято) —
  проглатывается молча (fail-safe, как весь остальной voice-стек) — сбой звука-
  маркера не должен блокировать сам push-to-talk.

### 4.4 `core/engine.py`
`_run_voice_question()`: одна строка `self.voice.play_beep()` перед
`self._voice_listener.record(config.VOICE_QUESTION_MAX_SEC)`. Работает
одинаково для хоткея и клика в UI — единая точка, без дублирования.

### 4.5 UI — `NewSpotterUI`
- `lib/api.ts`: `ptt_hotkey?: {ctrl: boolean; alt: boolean; shift: boolean; key: string}`
  в `SettingsState`.
- `lib/spotter-data.ts`: без изменений в статичном массиве `hotkeys` (те 5
  остаются презентационными константами) — новая строка рендерится отдельно,
  из `settings.ptt_hotkey` (динамическая, не из статичного массива).
- `components/spotter/views/hotkeys.tsx`: новая строка ниже статичного списка —
  `KeyCap` по `ptt_hotkey` (или «не задано», если `key` пусто) + кнопка
  «Записать». Захват: `onKeyDown` на документе в режиме записи, `preventDefault()`,
  собирает модификаторы + `event.key.toUpperCase()`, фильтр по разрешённому
  списку (A-Z/0-9/F1-F12), проверка коллизии с 5 фиксированными комбинациями
  (клиентская константа, зеркалящая `core/hotkeys.py::_HOTKEYS`) → при успехе
  `saveSettings({ptt_hotkey: {...}})`, при коллизии/невалидной клавише — короткое
  сообщение об ошибке, запись не сохраняется. Подпись под строкой: «Изменения
  вступят в силу после перезапуска Spotter App».

## 5. Обработка ошибок / граничные случаи

| Ситуация | Поведение |
|---|---|
| `ptt_hotkey` не задан / `key` пустой | 6-й хоткей просто не регистрируется — 5 фиксированных работают как раньше. |
| Клавиша занята другим приложением в системе | `RegisterHotKey` вернёт неудачу для id=6 — тот же fail-safe путь, что уже есть для 5 фиксированных (`registered.append` только при успехе), без падения. |
| Пользователь пытается забиндить уже занятую комбинацию (Ctrl+Alt+C и т.п.) | Отклоняется на клиенте до сохранения (сравнение с зеркалящей константой) — уменьшает шанс тихого конфликта, хотя финальная защита всё равно на бэкенде через факт неудачи `RegisterHotKey`. |
| `sounddevice`/устройство недоступны в момент `play_beep()` | Проглатывается молча, `_run_voice_question` продолжает (запись/распознавание не блокируются отсутствием звука-маркера). |
| Хоткей сработал во время критической реплики | Не изменяется — `ask_voice_question()` уже гейтит `is_critical_active` → `{"busy": true, "reason": "critical"}`, `play_beep()` в этом случае не вызывается вовсе (флоу не доходит до записи). |

## 6. Тестирование

- `tests/test_hotkeys.py` (новый или расширение существующего, если есть) —
  `_vk_from_settings()`: валидная комбинация → `(mods, vk)`; без модификатора →
  `None`; неразрешённая клавиша → `None`; A-Z/0-9/F1-F12 конвертируются верно.
- `tests/test_tts_playback_stream.py` — `play_beep()`: вызывает
  `_interrupt_playback()` первым; создаёт РОВНО один `sd.OutputStream`; `close()`
  происходит под тем же `self._stream_lock`, что и у `_play_wav` (тот же
  regression-паттерн, что уже используется для теста на крах ucrtbase.dll).
- `tests/test_engine_voice.py` — `_run_voice_question()` вызывает
  `voice.play_beep()` до `voice_listener.record()` (порядок вызовов через мок).
- Полный прогон `pytest` + `npx tsc --noEmit` зелёные.
- Ручная браузер-проверка: кнопка «Записать» захватывает комбинацию, валидация
  коллизий/неразрешённых клавиш показывает ошибку, сохранённое значение
  переживает `F5`. Живая проверка самого глобального хоткея в игре — вне
  скоупа автоматизации (нужен реальный F1 25 + физическая клавиатура), как и
  остальные пункты «живой проверки» в этом проекте.
