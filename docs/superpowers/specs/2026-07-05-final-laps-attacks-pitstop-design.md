# Final Laps / Attacks / Pit-Exit Mode — дизайн

Дата: 2026-07-05
Статус: утверждён пользователем (диалог 2026-07-05), реализация — по плану в
`docs/superpowers/plans/`.

## Проблема

Из исходного 18-пунктового пожелания пользователя: «сделать отдельный режим для
последних кругов, атак и пит-стопов, где реплики короче, плотнее и эмоциональнее».
Ядро Comment Planner (см.
`docs/superpowers/specs/2026-07-05-comment-planner-importance-design.md`, сдано и
проревьюено в предыдущей сессии) уже даёт:

- `laps_remaining <= 3` → +10 к важности (`score_importance`);
- `battle` (флаг борьбы за позицию) → +15 к важности;
- длина/эмоция реплики уже управляются числовой шкалой важности в `build_plan()`.

Но этого недостаточно для трёх конкретных сценариев:

1. **Последние круги** — числовой бонус влияет на важность лишь КОСВЕННО (через
   общую шкалу); директива LLM ничего не говорит явно про фазу гонки, и короткая
   длина срабатывает только если итоговая важность дотянула до 80.
2. **Атаки** (борьба за позицию, `battle=True`) — та же проблема: `+15` может не
   хватить, чтобы пересечь порог короткой длины (80), если у события низкая база.
3. **Пит-стопы** — F1 25 вообще не присылает событие «пит-стоп». Есть только
   телеметрия `pit_status` (0/1/2), которая сейчас используется ИСКЛЮЧИТЕЛЬНО для
   подавления вводящих в заблуждение строк про отрыв/темп (см. сессию Pit-Stop
   Fix, 2026-07-04) — реального голосового события на выезд из боксов нет.

## Согласованный объём (сознательно сужен в диалоге)

- **Последние круги + атаки** — расширение существующего `build_plan()`, без новых
  событий, без изменений `score_importance`.
- **Пит-стопы** — ТОЛЬКО выезд из боксов (не заезд), ТОЛЬКО в гонке (не
  практика/квалификация), как НОВОЕ синтетическое событие через `_enqueue_event()`
  (тот же паттерн, что `DAMAGE_*`/`F1_BENCH` — Python детектит переход, кладёт
  событие с уже собранными фактами, LLM формулирует фразу через обычный путь
  `build_plan()`/`Commentator.create()`, а не готовый текст).
- **Атаки** — используется существующий флаг `battle` (уже даёт +15 к важности и
  `reaction="атака"` через существующий `build_plan()`), НЕ отдельная система
  `core/race_ai` ATTACK/BATTLE (которая работает только при включённом Broadcast
  Overlay Mode через `create_broadcast()` — не трогаем в этом цикле).
- **Явно не в этом цикле:** заезд в боксы (только выезд), пит-стопы вне гонки,
  `race_ai` ATTACK/BATTLE broadcast-путь.

## Дизайн

### 1. Общий механизм «принудительная краткость/эмоция» в `build_plan()`

Финальные круги и атаки — оба случая «важность момента для зрителя выше, чем
формально набранное число». Вместо двух параллельных веток — одна проверка внутри
`build_plan()`:

```python
_force_urgent = (
    (event.get("laps_remaining") is not None
     and event["laps_remaining"] <= _FINAL_LAPS_THRESHOLD)   # тот же порог 3, что и в score_importance — НЕ новая константа
    or bool(event.get("battle"))
)
```

Если `_force_urgent`:
- `length` = `_LENGTH_SHORT` независимо от того, что дал бы обычный порог
  важности 80.
- Базовая эмоция принудительно берётся с ВЕРХА лестницы (`"на пределе"`) ДО
  применения персонального сдвига — персона всё ещё сдвигает результат на
  ступень (`calm` осядет на `"оживлённо"`, никогда не доходя до `"на пределе"`
  даже в самый напряжённый момент гонки — это соответствует характеру
  персоны-инженера, а не баг).
- `focus` получает явный маркер фазы — но **`plan.reaction` (короткая категория,
  например `"атака"`) маркер НЕ трогает** — он используется отдельно в строке
  директивы `"Тип реакции: {reaction}."` и должен остаться чистым словом.
  Маркер добавляется только в СТРОИТЕЛЬ `focus`: сегодня `build_plan()` берёт
  голый `reaction` как первую часть `focus` (`f"{reaction}: {driver} и
  {target}"` / `f"{reaction}: {driver}"` / просто `reaction`). Нужно ввести
  локальную переменную `focus_reaction` — по умолчанию равна `reaction`, а если
  `laps_remaining is not None and laps_remaining <= _FINAL_LAPS_THRESHOLD`,
  принимает значение `f"{reaction} (последние {laps_remaining} круга гонки)"`
  (число — как есть, без склонения; это системная директива для LLM, не
  финальная фраза для TTS — LLM сам сформулирует по-русски грамотно). Все три
  ветки построения `focus` (target/driver/ни один) используют `focus_reaction`
  вместо голого `reaction`. Если сработал только `battle` (без финальных
  кругов) — `focus_reaction` остаётся равен `reaction` без изменений: сам
  `reaction="атака"` уже достаточно ясен, лишнего текста в директиве не нужно.

**Откуда `build_plan()` берёт `laps_remaining`:** сейчас это поле существует
только внутри `PlanContext`, который строится в `_plan_context()` и используется
только для `score_importance()` — до `build_plan()` не доходит. Решение: в
`_enqueue_event()` (там, где уже вызывается `_plan_context()` для скоринга)
дополнительно проставить `event["laps_remaining"] = ctx.laps_remaining`
безусловно (не только при ошибке скоринга) — та же конвенция, что уже
используется для `event["importance"]`/`event["enqueued_at"]`: посчитано один
раз при постановке в очередь, дальше просто читается с самого события.
`battle` уже присутствует на событии — его кладёт `RaceState.enrich()` для
`OVTK`, отдельной проводки не требуется.

### 2. Новое событие `PIT_EXIT`

**Детекция (core/engine.py):** там, где уже обновляется
`self._player_pit_status = pl.get("pit_status")` (строка ~811), взять снимок
ДО обновления:

```python
prev_pit_status = self._player_pit_status
self._player_pit_status = pl.get("pit_status")
if (prev_pit_status in (1, 2) and self._player_pit_status == 0
        and self._session_type == "race"):
    self._enqueue_event({
        "event_code": "PIT_EXIT",
        "priority": "normal",
        "driver": "",
        "color": "#38BDF8",
        "tyre_compound": self._player_tyre_compound,
    })
```

Никакого отдельного флага «уже объявили» не нужно (в отличие от `DAMAGE_*`,
где severity может держаться выше порога много тиков подряд) — переход
`ненулевое → 0` физически может произойти только один раз за один заезд в
боксы, значение снова должно стать ненулевым (новый заезд), прежде чем сможет
повториться.

**Важность:** база 60 в `_BASE_IMPORTANCE` (тот же уровень, что `OVTK` — заметный
момент, но не разрушительный, как авария или штраф, поэтому идёт по обычному
пути гэпа/очереди, не по пути прерывания).

**Реакция/фокус:** `_REACTION_BY_CODE["PIT_EXIT"] = "выезд из боксов"`. Код
состава как есть — S/M/H/I/W; LLM уже проинструктирован в
`personas.py::_TYRE_GLOSSARY` переводить эти буквы на русский сам, дублировать
маппинг код→слово в `planner.py` не нужно — тогда это была бы ТРЕТЬЯ копия
одного и того же маппинга рядом с `core/packets.py::TYRE_VISUAL` и
`personas.py`.

**Важно — единая точка построения `focus`, а не отдельная ветка для `PIT_EXIT`:**
`tyre_compound`-ветка встраивается в ТУ ЖЕ последовательность проверок
`build_plan()`, что и `target`/`driver`/пусто из раздела 1, и использует ТОТ ЖЕ
`focus_reaction` (не голый `reaction`) — иначе `PIT_EXIT`, случившийся на
последнем круге гонки, молча потерял бы маркер финальных кругов. Порядок
проверок (первое совпадение побеждает):

```python
if tyre_compound:
    focus = f"{focus_reaction}: свежий комплект {tyre_compound}"
elif target:
    focus = f"{focus_reaction}: {driver} и {target}"
elif driver:
    focus = f"{focus_reaction}: {driver}"
else:
    focus = focus_reaction
```

`tyre_compound` идёт первой веткой без риска конфликта — `PIT_EXIT` никогда не
несёт `driver`/`target` (событие всегда про игрока, см. `"driver": ""` в
детекции выше).

## Файлы

| Файл | Действие |
|---|---|
| `commentator/planner.py` | `build_plan()` — принудительная краткость/эмоция; `_BASE_IMPORTANCE`/`_REACTION_BY_CODE` — запись `PIT_EXIT` |

## Отказоустойчивость

Ничего нового не добавляется поверх существующей защиты: `build_plan()`
остаётся чистой функцией без I/O (вызов уже обёрнут в try/except в
`core/engine.py` из предыдущего плана); детекция `PIT_EXIT` — обычное
присваивание и сравнение, без новых точек отказа; событие идёт через уже
защищённый `_enqueue_event()`.
