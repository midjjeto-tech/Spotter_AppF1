# Damage Tracking & Collision Notifications — Design Spec

**Дата:** 2026-07-05
**Статус:** утверждён (дизайн), готов к плану реализации
**Источник:** пользователь заметил, что приложение не парсит повреждения машины и не
уведомляет об авариях на трассе; выбрано как первый из двух пунктов («Повреждения +
аварии вместе»), второй («формат комментариев») — отдельный, более поздний цикл.

## 1. Обзор

Сегодня `core/packets.py::parse_player_damage()` читает из Car Damage (packet 10)
ТОЛЬКО `m_tyresWear[4]` (износ шин, уже используется). Все остальные поля повреждений
(крылья, пол/днище, коробка, двигатель) не парсятся вообще. Событие `COLL`
(столкновение) не зарегистрировано в таблице событий вообще — даже если игра его
шлёт, `parse_event()` его отбрасывает как нерелевантное.

Фича даёт игроку (только СВОЯ машина — см. §3):
1. **HUD** — 4 категории повреждения кузова (не шины — те уже есть отдельно).
2. **Голос на аварии** — мгновенная реплика при столкновении с участием игрока.
3. **Голос на повреждении** — реплика один раз за гонку на категорию, при переходе
   через порог «заметности».

## 2. Категории повреждений (не сырые поля)

F1 25 CarDamageData (packet 10), офсеты подтверждены косвенно — уже существующий
тест `test_parse_player_damage_wear_average` использует `stride = 42` как
«правдоподобный размер структуры», что совпадает с полной раскладкой ниже (42 байта
итого). Тем не менее, **как и с `pit_status` ранее, точные значения стоит сверить с
`diag_lap_offsets.py`-подобным скриптом на живой телеметрии перед тем, как полностью
доверять — включаем это в план как обязательный шаг, не рекомендацию.**

| Байт (от начала CarDamageData) | Поле F1 25 | Категория |
|---|---|---|
| 24 | `m_frontLeftWingDamage` | **Крылья** (max из 24/25/26) |
| 25 | `m_frontRightWingDamage` | **Крылья** |
| 26 | `m_rearWingDamage` | **Крылья** |
| 27 | `m_floorDamage` | **Аэродинамика/пол** (max из 27/28/29) |
| 28 | `m_diffuserDamage` | **Аэродинамика/пол** |
| 29 | `m_sidepodDamage` | **Аэродинамика/пол** |
| 32 | `m_gearBoxDamage` | **Коробка передач** |
| 33 | `m_engineDamage` | **Двигатель** |

Каждая категория — 0-100 (%), берём МАКСИМУМ среди своих полей (одно сильно
повреждённое крыло важнее, чем среднее). `_NOTICEABLE_THRESHOLD = 20` (%) — ниже
не считаем «повреждением» для целей голосовой реплики (мелкие царапины — постоянный
шум телеметрии, не то, что должно спамить голосом). HUD показывает точные проценты
всегда, вне зависимости от порога.

## 3. Область действия — только игрок

И повреждения, и аварии — только про машину игрока. Столкновение между двумя
чужими машинами не отслеживается и не озвучивается (сознательное сужение, не
пропуск — если понадобится позже, легко расширить тем же кодом путём смены фильтра).

## 4. Авария (`COLL`)

- `EVENT_DESCRIPTIONS["COLL"] = "Столкновение"` (делает код «релевантным» через
  существующий `RELEVANT_EVENTS = set(EVENT_DESCRIPTIONS.keys())`) + добавить в
  `CRITICAL_EVENTS` (авария — не менее важна, чем штраф/ретайр, должна получать тот
  же приоритетный голосовой путь).
- `parse_event()` — новая ветка `elif code == "COLL" and len(payload) >= 2:`,
  зеркалит уже существующую ветку `OVTK` (`struct.unpack_from("<BB", payload, 0)`),
  даёт `details = {"vehicle1_idx": v1, "vehicle2_idx": v2}`.
- `core/engine.py::_event_involves()` — расширить множество `involved` полями
  `event.get("vehicle1_idx")`/`event.get("vehicle2_idx")` — тогда УЖЕ существующий
  фильтр «участвует ли игрок» подхватывает `COLL` бесплатно, без новой отдельной
  функции.
- Голосовая реплика фиксирует ОБЕ стороны по именам (аналогично тому, как `OVTK`
  сейчас резолвит `overtaking_idx`/`being_overtaken_idx` в реальные имена через
  `self.race_state.driver(idx)["name"]`), фиксируется мгновенно (не откладывается,
  как и `OVTK`).

## 5. Модель данных повреждений + анти-спам

```python
# core/packets.py::parse_player_damage() — новые ключи в возвращаемом словаре
{
    "tyre_wear": float,        # уже существует, не трогаем
    "wing_damage": int,        # 0-100, max(front_left, front_right, rear)
    "floor_damage": int,       # 0-100, max(floor, diffuser, sidepod)
    "gearbox_damage": int,     # 0-100
    "engine_damage": int,      # 0-100
}
```

**Уточнение относительно исходного дизайна (найдено при подготовке плана):**
`state["telemetry"]` НЕ содержит `tyre_compound`/`tyre_age`/`tyre_wear` сегодня —
эти поля лишь обновляют приватные атрибуты движка (`self._player_tyre_*`, только
для `RaceTimeline`/`driver_coach`), во фронтенде (`NewSpotterUI/lib/api.ts`) их нет
вообще. Значит, «расширить существующий tyre_compound-паттерн» — не откуда
расширять. Вместо этого — новый выделенный ключ `state["damage"]` (тот же подход,
что уже использован для `state["f1_benchmark"]`/`state["career_memory"]`): свой
словарь, своя Panel во фронтенде, ничего существующего не трогаем и не ломаем.

```python
# state["damage"] (в /api/state) — обновляется в ветке PACKET_CAR_DAMAGE
{"wing_damage": int, "floor_damage": int, "gearbox_damage": int, "engine_damage": int}
```

Анти-спам — по образцу уже существующего паттерна `_f1_best_ms`/`_career_best_ms`
(флаг «уже объявляли» вместо порогового «лучше/хуже»):

```python
# core/engine.py — новое состояние в __init__, сброс на SSTA/смене трассы
self._damage_announced: dict[str, bool] = {
    "wing": False, "floor": False, "gearbox": False, "engine": False,
}
```

При каждом тике — простая проверка ТЕКУЩЕГО значения против порога и ТЕКУЩЕГО флага
(без хранения «предыдущего тика», по образцу уже существующих трекеров в этом файле):

```
если severity >= _NOTICEABLE_THRESHOLD и _damage_announced[category] is False:
    поставить голосовое событие DAMAGE_<CATEGORY>, выставить флаг в True
если severity < _NOTICEABLE_THRESHOLD:
    сбросить флаг в False (готовим следующее объявление, если деталь снова пострадает)
```

Ремонт в боксах чинит деталь → severity падает ниже порога → флаг сбрасывается
автоматически → новая поломка той же детали позже в гонке объявляется заново. HUD-
число обновляется каждый тик независимо от анти-спама.

## 6. Обработка ошибок / граничные случаи

| Ситуация | Поведение |
|---|---|
| CarDamageData короче ожидаемого (`stride` не в правдоподобном диапазоне) | Уже обрабатывается существующей проверкой `if not (24 <= stride <= 80): return {}` — новые поля наследуют эту защиту, дополнительной не нужно. |
| `COLL` пришёл, но ни один индекс не совпадает с игроком | `_event_involves()` вернёт `False` — событие не озвучивается, ведёт себя как нерелевантное (как сейчас `OVTK` между двумя чужими машинами). |
| Повреждение уже выше порога с самого первого тика сессии | Механизм не различает «уже было выше» от «только что пересекло» — первый тик с `severity >= порога` и `_damage_announced[category] is False` озвучивается, как и любое другое пересечение. Это соответствует §5 буквально (проверка текущего значения и текущего флага, без «предыдущего тика»), а не исключение из него. |
| Смена трассы / SSTA | `_damage_announced` сбрасывается в `{wing: False, floor: False, gearbox: False, engine: False}` — как и остальные анти-спам трекеры в этом файле. |

## 7. Тестирование

- `tests/test_packets_gaps_tyre.py` (или новый `tests/test_packets_damage.py`) —
  `parse_player_damage()` возвращает все 4 новые категории, корректно берёт максимум
  среди своей группы полей, деградирует на коротком/битом пакете так же, как сейчас.
- `tests/test_packets_gaps_tyre.py` (или отдельный) — `parse_event()` для `COLL`:
  корректные `vehicle1_idx`/`vehicle2_idx`, `priority: "critical"`.
- `tests/test_engine_*.py` (новый) — `_event_involves()` распознаёт `COLL` для
  игрока в обеих позициях (`vehicle1_idx`/`vehicle2_idx`); голосовая реплика на
  аварии фиксирует оба имени; анти-спам повреждений: не звучит повторно ниже порога,
  звучит один раз при пересечении, звучит СНОВА после падения ниже порога и нового
  пересечения; сброс на SSTA/смене трассы.
- `diag_lap_offsets.py`-подобное расширение для живой сверки байт-офсетов
  CarDamageData перед тем, как полагаться на них в проде (тот же ритуал, что и с
  `pit_status`).
- Полный `pytest` + `npx tsc --noEmit` (эта фича не трогает фронтенд, кроме HUD —
  см. §8) зелёные.

## 8. HUD (кратко)

Отдельная маленькая панель в `NewSpotterUI`, читающая новый `state.damage` (см. §5),
с 4 категориями и цветовой шкалой (зелёный < порога, жёлтый/красный выше) — тот же
визуальный паттерн, что уже применён для «Эталон F1»/«Личный рекорд трассы» (номер/
чипы + собственное пустое состояние), точная вёрстка уточняется на этапе плана.

## 9. Вне рамок (будущее)

- Аварии/повреждения ЧУЖИХ машин (сознательно отложено, см. §3).
- Голосовая реплика на КАЖДОМ увеличении повреждения (только на пересечении порога).
- DRS/ERS fault-флаги (`m_drsFault`/`m_ersFault`) — не входят ни в одну категорию
  выше, отдельная потенциальная фича.
- Второй пункт исходного запроса пользователя («формат комментариев») — отдельный,
  более поздний цикл брейнсторминга.
