# Дождь через N минут — advisory инженера (Фаза 4, шаг 2/2) — дизайн

Дата: 2026-07-10
Статус: утверждён по объёму пользователем (диалог 2026-07-10: горизонт ≤30
минут). Реализация опирается на парсинг из шага 1 — см. предупреждение ниже.

## Контекст

Шаг 1 (парсинг) закрыт: `parse_session` отдаёт `rain_forecast` = ближайший
будущий дождливый сэмпл {`minutes`, `rain_pct`, `weather`} или `None`.
**Важно:** прогноз-массив имеет один известный, не закрытый кодом класс
ошибки офсета (целый-сэмпл сдвиг, см.
`2026-07-10-weather-forecast-parsing-design.md`) — пользователь решил
двигаться дальше без живой сверки. Advisory строится поверх этого допущения;
если позже окажется, что офсет неверен, `rain_forecast` начнёт молчать
(самый частый исход при сдвиге) или изредка давать неверные минуты/% — ни то,
ни другое не ломает приложение, просто фраза будет неточной/отсутствующей.

## Проблема

`rain_forecast` парсится, но никуда не доходит: не хранится в engine-state,
не превращается в реплику. Игрок должен сам смотреть на HUD погоды.

## Решение (одним абзацем)

`core/engine.py` сохраняет `rain_forecast` из каждого `PACKET_SESSION` в
`self._rain_forecast` (тот же паттерн, что `self._track_id`). Новый чистый
трекер `core/strategy_ai/weather_advisory.py::RainAdvisoryTracker` — «armed
once» состояние (по образцу `BoxCallTracker`, но без эскалации: дождь — это
однократный heads-up, не команда, повторять/нагнетать не нужно): пока
прогноз показывает дождь В ПРЕДЕЛАХ ГОРИЗОНТА (≤30 минут) — объявляем РОВНО
ОДИН РАЗ; сброс, когда прогноз снова становится сухим ИЛИ дождь ушёл за
горизонт (>30 мин) — тогда следующее появление дождя в горизонте считается
новым эпизодом и объявляется заново.

## Автономные решения (нужен review пользователя)

1. **Горизонт 30 минут** — подтверждено пользователем явно, не мой выбор.
2. **Без гейта по session_type** — в отличие от гэп-дайджеста (Фаза 2, race-
   only, т.к. гэп к сопернику бессмыслен вне гонки), погода актуальна ВО ВСЕХ
   типах сессий (практика/квалификация/гонка) — решение по аналогии с
   box-вызовом Фазы 1 (тоже не гейтован), не гэп-дайджестом.
3. **Один heads-up, без повтора/эскалации** — в отличие от box-вызова
   (сознательно эскалирует, если игрок игнорирует команду), дождь — не
   команда, которую надо выполнить, а информация. Повторять её раз в 20с,
   пока дождь остаётся в горизонте, было бы утомительно.
4. **Фраза — фиксированный шаблон** (без LLM), как box-вызов, а не через
   обычный LLM-пайплайн (в отличие от `PIT_CALL_NOTICE`) — потому что здесь
   нет «второй реплики от комментатора» в этой фиче (пользователь просил
   именно инженерскую подсказку, не парную реплику диктора), а разовое,
   предсказуемое сообщение не требует творчества LLM.

## Не входит в объём

- «Трек подсыхает» / переход дождь→сухо — не запрошено, не строим.
- Повторное предупреждение по мере приближения дождя (например, ещё раз на
  10 мин) — сознательно не делаем (см. решение 3).
- Трек-лимиты — отдельная будущая подфича Фазы 4 (см. ограничение про
  пересечение с `PENA`, зафиксировано в CONTEXT.md).

## Архитектура

### `core/strategy_ai/weather_advisory.py`

```python
RAIN_ADVISORY_HORIZON_MIN = 30

class RainAdvisoryTracker:
    """Однократный heads-up «дождь через N минут» — armed once, без эскалации
    (в отличие от BoxCallTracker). Сброс, когда дождь уходит из горизонта
    или прогноз становится сухим — следующее появление снова объявляется."""

    def __init__(self) -> None:
        self._armed = False

    def check(self, rain_forecast: dict | None) -> str | None:
        """rain_forecast: {"minutes", "rain_pct", "weather"} или None.
        Возвращает готовую фразу один раз за эпизод, либо None."""
        if rain_forecast is None or rain_forecast["minutes"] > RAIN_ADVISORY_HORIZON_MIN:
            self._armed = False
            return None
        if self._armed:
            return None
        self._armed = True
        return _phrase(rain_forecast["minutes"], rain_forecast["rain_pct"])

    def reset(self) -> None:
        self._armed = False


def _phrase(minutes: int, rain_pct: int) -> str:
    min_word = ru_plural(minutes, "минуту", "минуты", "минут")
    pct_word = ru_plural(rain_pct, "процент", "процента", "процентов")
    if minutes <= 5:
        return f"Дождь через {minutes} {min_word}, вероятность {rain_pct} {pct_word}. Готовь интермедиэйты."
    return f"Дождь ожидается через {minutes} {min_word}, вероятность {rain_pct} {pct_word}."
```
(Числа — простые целые, `num_to_words`/движок TTS уже читает их естественно,
без спецобработки, см. докстринг `core/num_to_words.py`.)

**Пост-ревью правка (2026-07-11):** первая версия использовала
неизменяемое «{minutes} минут»/«{rain_pct} процентов» — грамматически
неверно для n%10==1 (нужно «1 минуту») и n%10 в 2-4 (нужно «минуты»),
особенно заметно в срочной ветке `minutes<=5`, где 4 из 5 значений (1-4)
требуют не ту форму. Ревью нашло это; исправлено вынесением общей
`ru_plural(n, one, few, many)` в `core/num_to_words.py` (рефакторинг
существующего приватного `_minute_word()` — теперь делегирует в неё,
поведение не изменилось) и применением с падежно-верными формами
(«минуту», не «минута» — винительный падеж контекста «через N минут», в
отличие от `_minute_word`, где контекст другой — самостоятельная
длительность). Заодно поймана опечатка «интермедиейты» →
«интермедиэйты» (сверено с `commentator/personas.py`). Тесты: 4 новых в
`tests/test_weather_advisory.py`, 5 новых в `tests/test_num_to_words.py`
(включая проверку, что рефакторинг `_minute_word` не сломал поведение).

### `core/engine.py`

`__init__`, рядом с `self._track_id`:
```python
self._rain_forecast: dict | None = None
self._rain_advisory = RainAdvisoryTracker()
```

В блоке `if packet_id == PACKET_SESSION:` (после `session = parse_session(data)`,
рядом с уже существующей обработкой `total_laps`/`track_id`/`session_type`):
```python
self._rain_forecast = session.get("rain_forecast")
phrase = self._rain_advisory.check(self._rain_forecast)
if phrase is not None:
    self._enqueue_event({
        "event_code": "ENGINEER_RAIN_ADVISORY", "priority": "normal",
        "phrase": phrase, "speaker": SPEAKER_ENGINEER,
        "driver": "", "color": "#38BDF8",
        "bypass_speak_threshold": True,
    })
```
`bypass_speak_threshold` — та же причина, что у `PIT_CALL_NOTICE`/
`ENGINEER_GAP_DIGEST`: разовое важное сообщение не должно молча тонуть из-за
недавней другой озвучки. Фраза преднабрана (`event["phrase"]`) → минует
LLM/templates.render(), тот же короткий путь, что у `ENGINEER_GAP_DIGEST`.

**Сброс на новой сессии** — в блоке `if code == "SSTA":`, рядом с
`self._gap_digest.reset()`:
```python
self._rain_advisory.reset()
```

## Граничные случаи

- **Дождь то появляется, то пропадает из прогноза около горизонта** (48↔52
  минут, к примеру) — не относится к этой фиче: горизонт 30 мин, дребезг
  ВОЗЛЕ 30 может переармировать чаще, чем хотелось бы. Принятое ограничение
  первой версии (симметрично дребезгу box-call/gap-digest), не усложняем
  гистерезисом.
- **Дождь уже идёт** (`weather` текущий ≥3, не прогноз) — эта фича его не
  озвучивает (это `out["weather"]`, не `rain_forecast`) — игрок и так видит
  дождь. Вне объёма.
- **Офсет прогноза окажется неверным** (см. «Контекст») — либо `None`
  всегда (тихо, ничего не сломано), либо изредка неверные минуты/% — фраза
  прозвучит один раз с неточным числом, не критично для heads-up.

## Тестирование

- `tests/test_weather_advisory.py` (новый) — чистая логика `RainAdvisoryTracker`:
  дождь в горизонте → фраза один раз; повторный тик с тем же прогнозом →
  `None` (не повторяем); дождь ушёл за горизонт (>30) → сброс, `None`;
  прогноз стал `None` (сухо) → сброс; после сброса дождь СНОВА в горизонте →
  новая фраза (новый эпизод); `reset()` вручную.
- `core/engine.py` — проводка (`_rain_forecast`, `SSTA`-сброс) — по образцу
  уже принятой конвенции (напрямую не юнит-тестируется полный тик, только
  через существующий `engine`-fixture, если есть точка входа для теста).
- Живая проверка (звучит ли фраза адекватно, не мешает ли) — у пользователя;
  плюс всё ещё висящая живая сверка прогноза дождя из шага 1.
