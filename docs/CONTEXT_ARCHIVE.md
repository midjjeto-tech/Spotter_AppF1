## Сессия 2026-07-04 (продолжение) — Career Memory: личный рекорд трассы, 6/6 ✅

Новая независимая фича — игрок сравнивается с СОБСТВЕННОЙ историей на трассе (не с
реальным F1, это отдельная killer-фича `f1_benchmark`). Все 6 задач плана
`docs/superpowers/plans/2026-07-03-career-memory.md` реализованы через
subagent-driven-development, двухступенчатое ревью (spec-compliance + code quality)
на каждую, все approved.

**Файлы:** `analytics/archive.py` (сводки сессий теперь отдают `track_id`),
`core/career_memory.py` (новый — класс `CareerMemory`), `core/engine.py` (state +
голосовые события + фикс analytics_context), `core/race_story.py` +
`commentator/story.py` (новый факт `vs_last_visit` для Post-Race Story),
`NewSpotterUI/lib/api.ts` + `.../views/race.tsx` (панель «Личный рекорд трассы»).

**Два разных эталона — НЕ ПУТАТЬ:**
- `best_ever` — лучший круг+секторы за ВСЮ историю трассы, ФИКСИРОВАННАЯ цель. Кормит
  HUD-панель и голосовые события `CAREER_PB`/`CAREER_SECTOR_PB` (личный рекорд, полный
  круг ИЛИ сектор).
- `last_visit` — данные САМОЙ ПОСЛЕДНЕЙ прошлой сессии на трассе (лучший круг +
  финишная позиция). Кормит ТОЛЬКО факт `vs_last_visit` в Post-Race Story — это
  нарратив "прогресс с прошлого раза", не заявка на рекорд.

Оба считаются из одного и того же скана архива, но у них разные потребители и разный
смысл — путаница здесь была бы тихим логическим багом, не крашем.

**Именование событий/полей:** `CAREER_PB`/`CAREER_SECTOR_PB` — свои события Career
Memory, отдельные от уже существующих `F1_BENCH`/`F1_SECTOR_BENCH` (сравнение с
реальным F1, не с собственной историей игрока). `state["career_memory"]` — отдельное
HUD-поле от `state["f1_benchmark"]`. Факт `vs_last_visit` в Post-Race Story отдельный
от уже существующих `weak_sector`/`weak_sector_vs_f1`.

**Фикс `analytics_context` (важно для будущих фич, трогающих контекст LLM):**
`core/engine.py::_refresh_analytics_context()` (строки ~1567-1572) теперь объединяет
`self._f1_context_line` и `self._career_context_line` в одну строку перед вызовом
`set_analytics_context()` — раньше Career Memory затёрла бы контекст F1-бенчмарка
(и наоборот), т.к. `set_analytics_context()` просто перезаписывал одну общую строку.
**Любая БУДУЩАЯ фича, которая хочет кормить `analytics_context` LLM, обязана завести
свою именованную переменную (`self._xxx_context_line`) и пройти через
`_refresh_analytics_context()`, а не звать `set_analytics_context()` напрямую** —
иначе баг с затиранием тихо вернётся.

**Фильтр-конвенция (переиспользована из `f1_benchmark`):** `CareerMemory` фильтрует
архивные сессии по `track_id` (числовой enum) + `session_type == "race"` — та же
конвенция, что и `F1Benchmark`, выбрана намеренно из-за прошлого бага ("Unknown"
трасса у пользователя, см. сводку сессии 2026-07-02 в «Архив старых сессий» ниже) —
сравнение по `track_name` (строка) ненадёжно, `track_id` — нет.

**Верификация:** `tests/test_career_memory.py` (новый) + `tests/test_engine_career_memory.py`
(новый) + правки в `tests/test_race_story.py`/`tests/test_story_generator.py` под новый

## Сессия 2026-07-04 — OpenF1 401: прозрачность в UI + сид-фолбэк для секторов ✅

Пользователь предложил «два режима — free historical mode и live mode», чтобы 401 от
OpenF1 не «ронял» приложение. Проверка кода ДО правок показала: падать там нечему —
`_get()` уже отдаёт устаревший кэш при сбое сети, `compare()["sectors"]` просто `None`
без исключений. Реальные проблемы (подтверждены пользователем как то, что нужно решить):
(1) UI молча прячет секторные чипы без объяснения ПОЧЕМУ; (2) кэш-фолбэк работает,
только если для трассы УЖЕ был хоть один успешный запрос — для "холодного старта" во
время блокировки резервных данных взяться неоткуда.

**Реализация:**
- `core/openf1_client.py::OpenF1Client` — новый `blocked_by_live_session: bool`. `_fetch()`
  отдельно ловит HTTP 401 (лог на INFO, не WARNING — штатный случай), ставит флаг;
  сбрасывается любым успешным ответом. Флаг трогается ТОЛЬКО реальной сетевой попыткой —
  чистый кэш-хит его не меняет.
- Новый `core/openf1_seed.py` — `SECTOR_SEED: dict[circuit_id, {...}]`, статический
  фолбэк на случай "нет ни живых, ни кэшированных данных". **Практически пустой** —
  OpenF1 заблокирован (401) не только для игроков, но и для разработки прямо сейчас
  (перепроверено дважды в этой сессии, без изменений); нечем наполнять. См. «Открытые
  баги/задачи» — по аналогии с `CIRCUIT_ID_TO_OPENF1_LOCATION`.
- `core/f1_benchmark.py::_load_sectors()` — приоритет: живые/кэш данные (`sectors_source
  ="api"`) → сид (`"seed"`) → ничего (`None`). `sectors_blocked` — была ли последняя
  сетевая попытка заблокирована 401. `compare()` отдаёт оба ключа ВСЕГДА (тот же
  контракт, что у `"sectors"`).
- `core/engine.py`/`NewSpotterUI/lib/api.ts` — прокидывают оба поля в state/тип.
- `race.tsx` — если секторов нет И `sectors_blocked` — короткая строка «Секторы
  недоступны — идёт live-сессия F1» вместо тишины; если секторы из сида — пометка
  «ИСТОРИЧЕСКИЕ ДАННЫЕ» рядом с чипами (не выдаём архив за свежие данные сезона).

**Живая память задним числом:** снова 4 сессии целиком в живом файле — сжата самая
старая позиционно («LLM-персона "инженер"»), см. `docs/CONTEXT_ARCHIVE.md`.

**Гонка с параллельной сессией (не моя правка, зафиксировано для памяти):** во время
финального прогона тестов поймал переходное состояние ДРУГОЙ параллельной сессии —
`tests/test_engine_pit_tracking.py` ожидал `RaceTimeline.record_snapshot(pit_status=...,
pit_lap=...)`, а `commentator/timeline.py` их ещё не поддерживал (2 упавших теста).
Повторный прогон секунды спустя — уже 0 failed (та сессия дописала сигнатуру). Не трогал
чужой код, только перепроверил после того, как всё устаканилось.

**Верификация:** `tests/test_openf1_client.py` (+4: 401 ставит флаг, прочие коды — нет,
успех сбрасывает, чистый кэш-хит не трогает), `tests/test_f1_benchmark.py` (+4: контракт
ключей, blocked, сид-фолбэк, ни сида ни данных). `npx tsc --noEmit` — чисто. Полный
прогон: **799 passed, 1 skipped, 0 failed**.

## Сессия 2026-07-04 — Краш SpotterApp.exe в фоне (access violation, sounddevice race) ✅

Пользователь пожаловался: "Spotter App вызывает подвисание и резко крашится в фоне".
Root cause найден через systematic-debugging (Phase 1-3) БЕЗ единой правки кода —
сразу по трём независимым источникам evidence:

1. Журнал Windows (`Get-WinEvent` -FilterHashtable Application/"Application Error") —
   **3 идентичных краша** `SpotterApp.exe`, все `Exception code: 0xc0000005`
   (ACCESS_VIOLATION) в `ntdll.dll`, **одинаковый `Fault offset`** во всех трёх
   (2026-06-28, 2026-07-04 ×2) — детерминированный баг, не случайный шум.
2. `dist/spotter.log` — НИ ОДНОГО Python-исключения перед крашами; лог обрывается
   через 1-2с после `YandexSpeech OK: ... (N samples)` (синтез успешен, ДО
   воспроизведения) — подтверждает нативный сегфолт, не Python-исключение (поэтому
   `except Exception` в коде его не ловил и не логировал).
3. Код (`voice/tts.py::_play_wav`) — единственный живой путь воспроизведения
   использовал МОДУЛЬНЫЙ глобальный `sd.play(data, sr); sd.wait()` (в потоке
   `TTSQueue._worker`). Параллельно, при critical-приоритетной фразе (safety car,
   пенальти — `core/packets.py::CRITICAL_EVENTS`), `TTSQueue.enqueue()` СИНХРОННО
   из ДРУГОГО потока (`core/engine.py::_commentary_loop`/ambient/voice-Q&A) звало
   `Voice._interrupt_playback()` → модульный `sd.stop()`. Обе функции делят один
   глобальный указатель стрима процесса — гонка при старте нового стрима одним
   потоком и `stop()` другим → access violation в PortAudio/WASAPI, убивает процесс
   целиком. Разработчик уже чинил ЭТУ ЖЕ проблему для микрофона
   (`voice/listener.py::_default_recorder`, есть явный коммент в коде про конфликт
   с TTS-воспроизведением), но для воспроизведения фикс сделан не был. Первый краш
   (28.06) случился ДО появления push-to-talk (02.07) — обычные critical-события
   комментатора уже сами по себе триггерят гонку.

**Фикс:** `voice/tts.py` — `_play_wav` теперь создаёт выделенный `sd.OutputStream`
на каждый вызов, публикует его в `self._current_stream` под `self._stream_lock`;
`_interrupt_playback` зовёт `.abort()` именно на этот объект (не на модульный
глобал) — тот же принцип, что уже применён для `InputStream` в `listener.py`.
`stream.stop()` (блокирует до допроигрывания буфера) заменяет `sd.wait()`.

**Верификация:** новый `tests/test_tts_playback_stream.py` (4 теста, фейковый
`sounddevice` через `sys.modules` — паттерн внедрения зависимостей как у
`VoiceListener(recorder=...)`): проверяет, что `_interrupt_playback`, вызванный из
ДРУГОГО потока, пока `_play_wav` блокируется в записи, абортит именно текущий
активный стрим, и что без активного воспроизведения — no-op. Полный прогон:
**766 passed, 1 skipped, 0 failed** (было 756 на предыдущей сессии 07-04, без
регрессий).

**Известная gotcha записана** — см. «Известные gotchas» в `CONTEXT.md`
(`sounddevice: модульный sd.play/wait/stop нельзя мешать между потоками`).

## Сессия 2026-07-04 — LLM-персона "инженер" (calm): обращение к игроку по имени ✅

Пользователь: «как инженер пилота, обращайся к игроку по имени — "Макс, через 2 круга
пит-стоп"». Прошли brainstorming (не сразу в код — фича, не баг): выяснилось, что пример
пользователя буквально относится к ШАБЛОННЫМ радио-репликам `commentator/radio.py`/
`strategist.py` (CHANNEL_RADIO), а не к LLM — пользователь осознанно выбрал ограничить
скоуп ТОЛЬКО LLM-персоной `"calm"` (уже описана как "инженер на пит-уолле"), шаблонные
пит-стопы/DRS/стратегия остаются безымянными.

**Реализация:**
- `core/ru_names.py::first_name_of(name)` — первое слово реального имени, `None` для
  служебных меток (`_SKIP_IN_GLOSSARY`, регистронезависимо) — fallback «просто не
  обращаться по имени», если имя неизвестно (кастомный пилот, данные UDP не пришли).
- `commentator/timeline.py::render()` — новый необязательный `player_name`; при наличии
  добавляет строку `ПИЛОТ: <Имя>.` в контекст для LLM. Без параметра — как раньше
  (обратная совместимость, все старые вызовы/тесты не тронуты).
- `core/engine.py::_build_ai_context()` — считает имя игрока через
  `race_state.driver(player_car_index)["name"]` → `first_name_of`, прокидывает в
  `render()`.
- `commentator/personas.py` — правка ТОЛЬКО текста персоны `"calm"`: инструкция
  обращаться по имени ИНОГДА (не в каждой фразе, для важных моментов), и НИКОГДА не
  выдумывать имя, если строки `ПИЛОТ` нет в контексте. `tv`/`hype`/`toxic` и общий
  `_OUTPUT_CONTRACT` не тронуты.

**Живая память задним числом:** к моменту этой сессии в CONTEXT.md уже накопилось 4
сессии целиком (параллельная сессия успела добавить «Краш SpotterApp.exe» и «Career
Memory», не сжав старые) — перед добавлением новой сжаты в архив «3 живых бага

## Сессия 2026-07-04 — 3 живых бага комментатора: спам, произношение, "обращение к себе" ✅

Пользователь прислал скриншот реальной ленты с тремя проблемами. Root cause каждой
найден через systematic-debugging (Phase 1-3) до правки кода — все три оказались
точечными, не архитектурными.

**1. Спам ("говорит без остановки").** Root cause: `config.MIN_COMMENT_GAP = 4.0` —
в насыщенной гонке (auto-режим, borьба рядом с игроком) значимое событие проходит
фильтр каждые 4-8с, и с таким маленьким зазором комментатор физически не замолкает.
Дополнительно: неограниченная `event_queue` + `_commentary_loop` слепо проговаривал
весь накопившийся бэклог по очереди — если события приходили быстрее, чем успевали
озвучиваться, комментатор "утюжил" уже устаревшие ситуации без пауз.
**Фикс:** `MIN_COMMENT_GAP` поднят до `9.0` (значение по-прежнему настраивается в
Settings UI, поменян только дефолт); новый метод `core/engine.py::
_is_stale_backlog_event()` — некритичное событие пропускается, если в очереди уже
ждут более свежие (проверено юнит-тестами `tests/test_commentary_backlog.py`, без
попытки гонять сам `while True`-поток).

**2. Произношение "Ферстаппен".** Эмпирически проверено через `piper.phonemize_espeak`
(тот же espeak-ng бэкенд, что использует офлайн-резерв Piper): default-ударение
espeak для "Ферстаппен" УЖЕ верное (`ˈɑ` перед "тап" = "ферстАппен") — текстовый
фикс для Piper был бы основан на ложной посылке и по gotcha выше ("потолок
акустической модели, не текста") мог только сломать то, что и так работает, поэтому
**Piper сознательно не тронут**. Для Yandex SpeechKit (основной путь) фикса не было
вообще — добавлен `core/pronunciation.py::apply_yandex()` (Yandex документированно
поддерживает `+` перед ударной гласной, в отличие от Piper/espeak, который читает
`+` как слово «плюс», см. `ru_textnorm.py`), подключён в
`yandex_ai/speech.py::YandexSpeech.synthesize()` перед вызовом API. Работает по всем
падежам фамилии (ударение не двигается при склонении).

**3. "Обращение к себе"** — если игрок в игре управляет машиной того же пилота,
что и реальный F1-эталон (например, выбрал Ферстаппена), `f1_benchmark.pb_line()`
всё равно называл эталон в третьем лице ("ты быстрее Ферстаппена на 0.3"), что
звучит как обращение к постороннему. **Фикс:** `core/f1_benchmark.py` — новый
`_is_player_reference()` (сравнение фамилий через уже существующий
`core.ru_names.surname_of`), `pb_line()`/`context_line()` получили опциональный
`player_name`; при совпадении — "твоего же быстрейшего круга" вместо фамилии.
`core/engine.py::_update_f1_benchmark()` теперь передаёт
`race_state.driver(player_car_index)["name"]`. Заодно найден и исправлен чистый
грамматический баг рядом (виден на скриншоте: "от быстрейший круг X" вместо "от
быстрейшего круга X") — `_ref_word()` возвращал именительный падеж после предлога
"от"/сравнения "быстрее", требующих родительного; теперь принимает `case` ("nom"/
"gen").

**Верификация:** `tests/test_f1_benchmark.py` (+5), `tests/test_pronunciation.py`
(новый, +5), `tests/test_commentary_backlog.py` (новый, +3); `_FakeBench` в
`tests/test_engine_f1_benchmark.py` обновлён под новую опциональную сигнатуру
(`player_name=None`) — иначе падал `TypeError`. Полный прогон: **756 passed, 1
skipped, 0 failed** (был 704 на 07-03 — рост частично от других незалогированных
изменений между сессиями, не только от этой).

**Незакрытое / честно:** respell для Piper не добавлен НЕ потому что забыли, а
потому что phonemize показал, что он не нужен для "Ферстаппен" конкретно — если
подобная жалоба всплывёт по другому имени, СНАЧАЛА гонять
`piper.phonemize_espeak.EspeakPhonemizer().phonemize("ru", word)` (venv уже имеет
`piper-tts` установленным, несмотря на то что `import piper_phonemize` как

## Сессия 2026-07-02 (продолжение) — Архив «Unknown» трасса: найден и исправлен реальный root cause ✅

**Жалоба пользователя:** архив сессий показывает "Unknown" вместо названия трассы у ВСЕХ
сохранённых заездов (скриншот: 3 сессии, все "Unknown", позиции P11/P22/P2 отображаются
верно). Формулировка "всё ещё сломан" — но запись в этом файле от 2026-06-29 утверждала,
что "Unknown" = старые сессии с `track_id=-1`, кода-бага нет. **Эта запись была
ОШИБОЧНОЙ** — не проверялось фактическое содержимое сохранённых JSON.

**Root cause (проверено чтением `dist/game_sessions/*.json`):** во всех 3 файлах
`track_id=29` (не -1!) — трасса определялась нормально. Проблема — в
`analytics/loader.py::TRACK_ID_TO_GP` и `core/f1_benchmark.py::TRACK_ID_TO_CIRCUIT`:
оба словаря мапили `track_id` (0–23) **в порядке календаря сезона 2025** вместо
реального `m_trackId` enum игры (комментарий в коде честно предупреждал "⚠️ NOT
VERIFIED on live packets" — и предположение оказалось неверным). Реальный enum
подтверждён официальной EA/Codemasters UDP-спекой + независимыми парсерами
(f1-2019-telemetry docs, f1-24-udp): `track_id=29` = **Jeddah** (Saudi Arabian GP),
индексы стабильны с F1 2019 и просто дополняются новыми трассами (Jeddah/Miami/Vegas/
Qatar/Zandvoort/Portimão получили id 26–32, а НЕ 0–23 как в старом словаре).

**Скрытый более серьёзный баг заодно пофикшен:** та же неверная таблица использовалась
в `/api/load_f1` (сравнение с реальным Гран-при) — сессии на треках, чей реальный id
совпадал с ЧУЖИМ индексом старой таблицы (напр. реальный Silverstone=7, а по старой
таблице 7=Monaco), **молча сравнивались бы с данными не того GP**, без единой ошибки.

**Фикс:** оба словаря пересобраны под верный enum (33 записи в `TRACK_ID_TO_GP` — 24
трассы текущего календаря + 8 legacy/short-трасс без текущего GP на понятных
названиях; 24 записи в `TRACK_ID_TO_CIRCUIT` — только текущий календарь, legacy
осознанно не включены, `load()` для них корректно вернёт `False`/`no_fastf1_data`).
`tests/test_f1_benchmark.py` — 7 мест `b.load(15, …)` (старый "Monza") заменены на
`b.load(11, …)` (новый верный id Monza). **archive.py/archive.tsx не трогали** — баг был
только в источнике данных, логика чтения/фильтрации была верна с самого начала.

**Верификация:** `TRACK_ID_TO_GP.get(29)` → `('Jeddah', 'Saudi Arabian Grand Prix')` ✅.
Полный прогон: **677 passed, 1 skipped** — без регрессий (совпадает с бейслайном).

**Незакрытое:** 3 уже сохранённых файла (`dist/game_sessions/*.json`) физически всё ещё
хранят `track_name: "Unknown"` (это строка в самом JSON, а не вычисляется на лету) —
для их отображения корректно нужен one-off бэкфилл по уже записанному `track_id` в тех
же файлах. Auto-mode классификатор заблокировал попытку сделать это молча (правильно —
перезапись существующих файлов пользователя требует явного да). **Спросить пользователя
напрямую, прежде чем трогать `dist/game_sessions/*.json`.** Новые заезды после этого
фикса будут показывать верное название автоматически, бэкфилл нужен только для
отображения этих 3 старых карточек прямо сейчас.

### Побочный фикс — комментатор озвучивал «Ничего не писать» (root-caused, не патч симптома)

**Корень:** `commentator/personas.py` просил LLM на «нечего сказать» вернуть ПУСТУЮ строку
через естественный язык («верни ПУСТУЮ строку (ничего не пиши)») — LLM ненадёжно выдают
truly-empty completion на такую просьбу и иногда просто ЭХОМ повторяют инструкцию как ответ.
`commentator/brain.py::create()` проверял только truthiness (`if phrase:`) — эхо инструкции
проходило как «реальная фраза» и озвучивалось.
**Фикс:** промпт теперь просит точный сентинел **ТИШИНА** (плюс сохранён путь через пустую
строку); `brain.py` получил `_is_silence()` — точное (не подстрочное) сравнение против набора
известных эхо-фраз (`тишина`, `ничего не писать`, `пустая строка` и вариации), чтобы не душить
реальные реплики, где эти слова встретились органично. Тесты: `tests/test_brain.py`
(+3: эхо-инструкция, сентинел с пунктуацией, живая фраза со словом «тишина» НЕ фильтруется).

### Побочный фикс — «роботичный» голос основного комментатора (спавнены/выполнены фоновые задачи)

По жалобе «звучит как робот, не живой» — проверено и исправлено (детали не в этой сессии
целиком, но подтверждено живым пробом с реальным ключом 2026-07-01/02):

### Гочта по тестам (Windows) — уточнение старой записи

Ранее в этом файле отмечалось «для итоговой строки pytest нужен флаг `-u`». **Уточнение:**
даже с `-u` итоговая строка (`N passed`) иногда всё равно обрезается демон-потоками Voice при

→ `_try_once` глотал → тихий фолбэк на v1. Тесты были зелёные, потому что мокали
`post_json`, возвращая **bytes** — мок не совпадал с реальным клиентом.

**Фиксы:**
- `yandex_ai/client.py`: новый `post_json_raw()` → возвращает сырые байты (`resp.read()`)
  для NDJSON-стрима v3.
- `yandex_ai/speech.py`: `_asynthesize_v3` использует `post_json_raw`; убран `folderId`
  из тела (в v3 нет такого поля → HTTP 400 «unknown field»; папка берётся из Api-Key);
  `audioEncoding` → `LINEAR16_PCM` (v3-энум, не `LPCM`); убран `audioChannelCount`.
- `speech.synthesize()`: явный INFO-лог «YandexSpeech OK: version=v3 …» при успехе и
  «OK via v1 fallback» — теперь в логах ВИДНО, реально ли v3 дошёл (task2.md п.1).
- `tests/test_yandex_version.py`: моки переключены на `post_json_raw`; новый регресс-тест
  `test_payload_has_no_folder_id_and_uses_raw_transport`.

### Почему ушли с MOSS-TTS-Nano

**MOSS-TTS-Nano не умеет русский.** Доказано пятью независимыми способами:
- 18 встроенных голосов — только китайские/английские/японские, русских ноль
- OpenMOSS = Fudan (китайская лаба); README говорит "multilingual" но без списка языков
- Токенизатор дробит русское предложение на 42 токена-огрызка (по буквам) vs 18 чистых сабвордов для английского → русского почти не было в обучении
- Живой тест: русский генерит на 60% больше аудио на символ, чем английский (модель мучается)
- На слух: «ломаная речь, проглатывает себя, звучит по-английски»

**Voice cloning это НЕ чинит:** клонирование переносит тембр, но произношение берётся из выученного маппинга текст→звук. Модель без русского = твой тембр, читающий русский английскими фонемами. Поэтому WAV-клонирование (прошлая сессия) сделало только хуже.

## Сессия 2026-06-28 — Полевые баги: шины "?" и имена "гонщик"

**Тест-бейслайн: 557 → 568 passed** (+11), 1 skipped, 1 pre-existing warning.

### Баг B (РЕШЁН): тип шин = "?" (и speed/gear/fuel смещены)

**Корневая причина:** `parse_player_status` и `parse_player_telemetry` использовали
`base = HEADER_SIZE + 1 + idx*SIZE` — лишний `+1`. Только `PacketParticipantsData`
имеет префикс `m_numActiveCars`; у `PacketCarStatusData`/`PacketCarTelemetryData`/
`PacketLapData` его НЕТ. Из-за `+1` чтение каждого поля сдвигалось на 1 байт:
`data[base+26]` читал m_tyresAgeLaps (offset 27) вместо m_visualTyreCompound (26) →
малое число не из TYRE_VISUAL → "?". Возраст читал FIA-флаг (offset 28) → "частично".

**Доказательство:** `parse_lap_data`/`parse_player_damage` (без `+1`) работают на живой
игре (позиции/износ верны) — та же структура «header + array». Если бы `+1` был верен,
compound читал бы код 16-18 → "M/H/S", никогда "?". Само "?" доказывает сдвиг.

**Фикс:** убран `+1` в обоих парсерах (`core/packets.py`). Тесты
`test_telemetry_sanity.py` и `test_packets_gaps_tyre.py` кодировали баг (фантомный
префикс-байт) — переписаны под реальный layout (без префикса) + добавлены кейсы с
ненулевым player_idx как независимый якорь. Тесты падали до фикса, проходят после.

### Баг A (ДИАГНОСТИКА): имена пилотов = "гонщик" даже у лидера

**Статус:** корневая причина не доказана без байтов из живой игры. `parse_participants`
парсит свой префикс `numActiveCars` корректно, а `race_state.driver()` независимо
добивает имя по номеру из `F1_2025_BY_NUMBER`. Чтобы ДАЖЕ лидер был "гонщик",
сам `raceNumber` должен быть неверным → почти наверняка **сдвиг layout
ParticipantData (формат F1 26?)** ИЛИ пакет Participants не приходит.

**Добавлена временная диагностика (env `SPOTTER_DIAG=1`):**
- `core/packets.py parse_participants` — на каждый пакет: num_active + по машинам
  idx/raceNumber/teamId/имя/первые 16 байт имени (hex).
- `core/f1_metadata.py enrich_drivers` — на машину: number/raw_name → resolved name/team.
- `core/engine.py` — один раз: packet_format/game_year/player_car_index из заголовка.

**Как пользоваться:** запустить `SPOTTER_DIAG=1 python app.pyw`, зайти в сессию F1,
прислать строки `DIAG ...`. Читать так:
- `raceNumber=81 name='PIASTRI'` → участники в норме, баг ниже по потоку.
- мусорный raceNumber / битое имя → сдвиг layout (нужен F1 26 ParticipantData).
- `num_active=0` или нет строк `DIAG participant` → пакет не приходит.
- `packet_format=2026` → подтверждённый F1 26 → добавить новый layout.

## Сессия 2026-07-05 (продолжение) — Comment Planner: важность события управляет живостью комментария, 6/6 ✅

Root cause документированного бага «спам комментатора» и «однообразный комментарий»:
LLM-комментатор на КАЖДОМ триггере свободно выбирал свою тему из всего таймлайна гонки,
поэтому мог пересказывать старую драму независимо от того, что реально только что
произошло. Фикс — не ещё один слой дедупа, а КОРЕНЬ: LLM больше не выбирает тему сама,
её выбирает Python ДО вызова LLM.

**Реализовано (6/6 задач плана `docs/superpowers/plans/2026-07-05-comment-planner-
importance.md`, spec: `docs/superpowers/specs/2026-07-05-comment-planner-importance-
design.md`, subagent-driven-development, двухступенчатое ревью на каждую, все approved):**

- `commentator/planner.py` (новый) — `score_importance()` даёт каждому событию оценку
  важности 0-100 (базовая таблица по `event_code` + модификаторы: игрок вовлечён +20,
  battle +15, последние круги +10) — критические события (`priority == "critical"`)
  всегда floor 90, старое поведение гарантированно сохранено. `build_plan()` строит
  директиву (фокус/реакция/длина/эмоция/must_mention) для LLM.
- `core/event_queue.py` (новый) — `ImportanceQueue`, drop-in замена `queue.Queue` поверх
  `queue.PriorityQueue` (важнее — раньше, FIFO при равенстве).
- `config.py` — 8 новых констант порогов (`PLAN_BASE_THRESHOLD` и т.д.); `PLAN_GAP_SKIP_
  THRESHOLD`/`PLAN_INTERRUPT_THRESHOLD` НАМЕРЕННО равны 90 (не совпадение) — это ЕДИНСТВЕННОЕ,
  что гарантирует сегодняшним critical-событиям одновременно и обнулённый гэп, и прерывание
  текущей озвучки; разведи их порознь без понимания — критическое событие может начать
  ждать гэп, но при этом всё равно прерывать чужую фразу (или наоборот). Закомментировано
  на месте, тест `test_gap_skip_and_interrupt_thresholds_share_same_value` это проверяет.
- `core/engine.py` — очередь событий теперь `ImportanceQueue`; новая точка-воронка
  `_enqueue_event()` считает `importance` один раз (фолбэк 50 + warning при падении
  planner'а — баг планировщика не может уронить движок) и проходят через неё ВСЕ 10
  старых мест `event_queue.put(...)`; новый decaying-порог `_speak_threshold()`
  (65→35 за 45с) молчит маловажные события ДО вызова LLM (экономия денег на API) — КРОМЕ
  ambient-тиков, у которых СОЗНАТЕЛЬНОЕ исключение (`not event.get("ambient")` в
  `_commentary_loop`): у ambient уже есть свой независимый адаптивный каданс (Task #14,
  `_ambient_loop`), второй фильтр поверх задушил бы его насмерть — не убирать это
  исключение, пытаясь «унифицировать» ambient под общий порог; `_is_stale_backlog_event(event, now)`
  переписан — было «не критично И в очереди есть что-то новее» (одинокое событие никогда
  не устаревало), стало «важность < 70 И висит в очереди дольше 20с по своему собственному
  штампу `enqueued_at`» (у каждого события своя независимая «жизнь»).
- `commentator/brain.py` — `_compose()` получил опциональный `plan`; когда он есть,
  первым блоком контекста LLM идёт «ЗАДАЧА: прокомментируй ИМЕННО это»; `plan=None`
  (ambient) — поведение байт-в-байт как раньше.
- `commentator/personas.py` — `_OUTPUT_CONTRACT`: инструкция «сам решай, что важно»
  теперь условная — действует, только если в контексте НЕТ блока «ЗАДАЧА».

**Два похожих, но РАЗНЫХ поля — НЕ ПУТАТЬ (как и в прошлых сессиях с этим паттерном):**
`priority` (строка `"critical"`/др.) — СТАРОЕ поле, им по-прежнему и без изменений
питаются `SituationDedup`, session guard и флэшбек-тишина. `importance` (число 0-100) —
НОВОЕ, отдельное поле, живёт РЯДОМ с `priority`, не заменяет его. Это НЕ новый слой
дедупа поверх `SituationDedup` (проект уже отклонял добавление слоёв дедупа как
неправильный фикс повторов, см. «Известные gotchas» — спам-баг) — `SituationDedup`
как занималась своим делом независимо, так и занимается; фикс этой сессии устраняет
корневую причину рассинхрона триггер↔тема, а не маскирует симптом ещё одним фильтром.

**Отложено на будущее (по design-спеке, сознательно не в этом плане):** пресет «финальные
круги/атака», «память гонки» (кто кого атаковал), расширение банка фраз
`commentator/templates.py`.

**Верификация:** полный прогон `py -3.12 -u -m pytest --ignore=tests/test_gpt.py -q` —
**865 passed, 1 skipped, 0 failed** (итоговая строка снова не пропечаталась — известная
Windows-особенность буферизации вывода pytest, посчитано через

## Сессия 2026-07-05 (продолжение) — Режим последних кругов / атак / выезда из боксов, 2/2 ✅

Мини-фича поверх уже сданного Comment Planner (см. сессию выше): закрывает два пункта,
отложенные его design-спекой на будущее — «финальные круги/атака» и голос для момента,
у которого раньше вообще не было реплики (выезд из боксов).

**`commentator/planner.py`:** `build_plan()` получил ОДНУ общую проверку «форс-срочность»,
на которую завязаны СРАЗУ два триггера — последние 3 круга гонки (`laps_remaining <= 3`,
тот же порог-константа, что уже используется в `score_importance()`, не второй дубль) и
активная борьба за позицию (`battle`). Раньше короткая/интенсивная подача включалась
только когда числовая важность переваливала за 80 — событие с борьбой или поздней гонкой,
но более низким базовым скором, могло проскочить недодраматизированным. Теперь любой из
двух триггеров форсит короткую реплику на верху эмоциональной лестницы НЕЗАВИСИМО от
итоговой оценки важности. Новый тип события `PIT_EXIT` (база важности 60, reaction
«выезд из боксов») заведён в те же таблицы планировщика и участвует в ТОЙ ЖЕ общей
проверке — выезд из боксов на последних кругах получает маркер срочности наравне со всеми,
не отдельный частный случай.

**Два похожих поля — НЕ ПУТАТЬ:** маркер финальных кругов вклеивается в `focus` (то, что
видит LLM как описание момента, например `"атака (последние 2 круга гонки): Норрис и
Пиастри"`), а НЕ в `reaction` — `reaction` остаётся чистой короткой категорией
(`"атака"`), её отдельно использует строка `"Тип реакции: ..."` в промпте. Если в будущем
маркер срочности случайно уедет в `reaction` — промпт получит мусор в категорийном поле,
которое должно быть коротким лейблом, а не описанием момента.

**`core/engine.py`:** (a) `_enqueue_event()` — единая воронка, через которую и так уже
проходит каждое событие в очереди, — теперь помимо `importance`/`enqueued_at` также
проставляет `event["laps_remaining"]`, считая его один раз из уже существующего
`PlanContext`; тот же fail-safe фолбэк (`None`), что и у остальных полей воронки — баг
планировщика по-прежнему не может уронить движок. (b) Новый эдж-детектор
`_maybe_announce_pit_exit(prev_status, new_status)` следит за переходом из пит-лейна (1
или 2) НАРУЖУ (0) по сырому телеметрийному `pit_status` — F1 25 не шлёт отдельное игровое
событие «пит-стоп», только этот телеметрийный байт (который ДО этой сессии использовался
только для подавления обманчивых строк отрыва/темпа во время самого пит-стопа, см. сессию
2026-07-04). Детектор фильтрует по типу сессии — работает только в гонке, не в
практике/квалификации, где пит-стопы происходят постоянно и не несут драмы. В отличие от
`DAMAGE_*` (см. сессию ниже, там анти-спам флаг `_damage_announced` был обязателен) —
здесь отдельный флаг не нужен: переход «был в боксах → выехал» физически может произойти
только один раз за один заезд в бокс, повторный анонс невозможен по конструкции перехода,
а не по внешнему сброс-флагу.

**Сознательно вне рамок (явные решения пользователя по ходу дизайна):** вход в боксы не
анонсируется (только выезд); выезд из боксов не озвучивается вне гонки; «атаки»
переиспользуют существующий флаг `battle`/пайплайн OVTK — отдельная система
`core/race_ai` ATTACK/BATTLE (работает только при включённом Broadcast Overlay Mode,
через `create_broadcast()`) не тронута.
