# Spotter App — Контекст разработки

## Правило ведения контекста

**После каждых 2 выполненных задач** — обновить раздел «На чём остановились» в этом файле:
- что сделано (кратко, по файлам)
- открытые задачи / баги
- следующие шаги

Счётчик задач живёт ТОЛЬКО в разделе «На чём остановились» ниже — не дублировать его
здесь. (Дублированный счётчик в этом абзаце и в «На чём остановились» рассинхронизировался
на несколько сессий, пока не заметили при реорганизации 2026-07-02 — см. архив.)

**Размер файла:** CLAUDE.md требует держать CONTEXT.md компактным (не больше ~100 пунктов).
Здесь — только живая архитектура, открытые задачи и последние ~3 сессии целиком. Более
старая история — однострочная сводка в разделе «Архив старых сессий» внизу + полный текст
в `docs/CONTEXT_ARCHIVE.md`. При добавлении новой сессии наверх (после «На чём
остановились») — не забывать сжимать самую старую из «последних трёх» в архив.

**Реорганизация 2026-08-13.** Файл вырос до 7240 строк (после реорганизации 2026-07-02
было 719): несколько параллельных сессий добавляли записи подряд, конвенция «последние
~3 сессии целиком» не соблюдалась с середины июля. Проведён отдельный заход: 96 сессий
(08-09 и старше) перенесены в `docs/CONTEXT_ARCHIVE.md`, закрытые строки таблицы багов —
туда же, пометки «Открыто» из архивируемого текста сверены с кодом и сведены в один
раздел ниже. Живыми оставлены сессии 08-10 и 08-11 плюс текущая работа.

**Правило на будущее, которое здесь нарушали дважды:** новая запись идёт НАВЕРХ, сразу
после «На чём остановились», а не в конец файла. Записи 08-11 и 08-13 приписывались в
конец и оказались оторваны от своего раздела.

## Что это

Десктопное приложение для F1 25. Принимает UDP-телеметрию от игры,
генерирует комментарии через YandexGPT (текст) + Yandex SpeechKit (голос);
офлайн-резерв голоса — Piper (русский, CPU/ONNX). UI через pywebview + HTML/JS.

**Проект ПОД GIT с 2026-08-06.** Baseline-коммит снят до уборки, тег `v0.1.0`.
Правило «не редактировать один файл из двух сессий» остаётся в силе (worktree
один), но потеря работы больше не безвозвратна.

**Оговорка, снятая 2026-08-14 не полностью.** Утверждение выше было верно не для
всего дерева: `.gitignore` неякорным шаблоном `racefeed/` скрывал `core/racefeed/`
и `tests/racefeed/` — 31 файл, весь модуль RaceFeed с тестами, никогда не был в

### Язык RaceFeed — принятый дизайн следующего рефакторинга

**Editorial Pacing** — session-wide отбор RaceFeed-публикаций, который удерживает
живую гонку в журналистском диапазоне 15–25 постов: рабочий бюджет 20, потолок
30 только для некритичных публикаций. _Не называть_: общий hard cap.

**Критичная RaceFeed-публикация** — финиш, SC/красный флаг, сход, ключевое
событие игрока, чемпионат или milestone; такая публикация не блокируется
Editorial Pacing budget даже после достижения потолка.

**Battle Story** — развивающаяся история обмена позициями между одной парой
пилотов: первый обгон открывает её, повторные обмены дают публикацию только при
значимом повороте или развязке. _Не называть_: один пост на каждый `OVTK`;
обгоны разных соперников не объединять.

**Analytics Budget** — максимум шесть смысловых RaceFeed-публикаций за гонку:
две про разрывы, две про шины и по одной про топливо и ERS. Это потолок, не
квота: тихая гонка может закончиться ниже общего диапазона 15–25 без
искусственного заполнения ленты.

**Incident Story** — один контактный эпизод одной пары пилотов в пределах
30 секунд или круга; повторные `COLL` не создают новые публикации. Контакт
игрока публикуется сразу, чужой — только при последствии; штраф, сход или SC
могут стать отдельным официальным развитием той же Story.

## Голосовой движок (voice/tts.py) — Yandex SpeechKit (основной) + Piper (офлайн-резерв)

### История движков TTS

1. Piper (английский) → заменён на Silero (русский, офлайн)
2. Silero v4_ru (локальный `.pt`, torch CPU) → заменён на Qwen3-TTS (сессия 2026-06-19)
   - Причина замены: задержка Silero ~500ms, нет streaming, блокировал телеметрию
   - Silero-код и папка `silero-models/` полностью удалены
3. Qwen3-TTS-0.6B (GPU, CUDA) → заменён на MOSS-TTS-Nano (сессия 2026-06-20)
   - Причина: GPU жрало VRAM во время F1 25 → фризы игры; нужен чистый CPU
4. MOSS-TTS-Nano-100M-ONNX → **заменён на Piper** (сессия 2026-06-21) — прожил ОДИН день
   - Причина: MOSS-TTS-Nano не поддерживает русский язык (доказано 5 способами:
     из коробки только кит./англ./яп. голоса; токенизатор дробит русское предложение
     на буквы-огрызки вместо сабвордов; +60% длины аудио на символ против английского;
     на слух — рваная, "английская" речь). Voice cloning это не чинит: произношение
     берётся из выученного текст→звук маппинга модели, а не из тембра голоса.
   - Старый MOSS-код (`new_tts/moss_tts.py`, `onnx_tts_runtime.py`, `ort_cpu_runtime.py`,
     `moss_tts_nano/`, `models/MOSS-*`) с тех пор полностью удалён из репозитория.
5. Piper (единственный движок) → добавлен **Yandex SpeechKit как основной** (сессия
   2026-06-22, см. `docs/superpowers/plans/2026-06-22-yandex-ai-commentator.md`) —
   облачный голос лучше по качеству; Piper остался офлайн-резервом на случай сбоя
   сети/ключа/квоты Yandex.

### Текущая архитектура (`Voice` + `new_tts/piper_tts.py` + `yandex_ai/`)

`Voice.__init__` (`voice/tts.py`) всегда создаёт `PiperVoiceEngine()` (офлайн, грузится в
фоновом потоке) как `self._engine`. Yandex SpeechKit подключается ОТДЕЛЬНО и позже —
через `voice.set_yandex(speech_source)` (из `core/engine.py`, когда есть валидный
API-ключ). Порядок выбора движка в `_synthesize()`:

```python
# voice/tts.py — упрощённо
if self._yandex is not None and self._yandex_healthy:
    audio, sr = self._yandex.synthesize(text, persona)   # облако, основной
    if ok:
        return audio, sr
    # синтез не удался → сразу Piper, БЕЗ таймаут-штрафа
if self._engine.is_ready:                                 # Piper — офлайн-резерв
    return self._engine.synthesize(text, persona)
```

`set_yandex_healthy(ok)` кормится health-monitor'ом `core/engine.py`: когда Yandex падает,
следующий вызов сразу уходит на Piper, без ожидания таймаута; когда снова здоров —
следующая фраза опять пробует Yandex. Если и Piper не загрузился — `_init_pyttsx3()`
(резерв последней надежды, см. `_wait_and_setup`).

**Piper (`new_tts/piper_tts.py`, класс `PiperVoiceEngine`):** пакет `piper-tts` (pip),
ONNX-инференс через `onnxruntime`, полностью CPU, без torch. 4 нативных русских голоса,
по одному на персону (`PERSONA_VOICE`, `length_scale` = скорость):

```python
PERSONA_VOICE = {
    "tv":    ("denis",  1.0),
    "hype":  ("denis",  0.92),
    "calm":  ("dmitri", 1.08),
    "toxic": ("dmitri", 1.0),
}
```

- Модели: `models/piper/ru_RU-{voice}-medium.onnx` (+ `.json`), ленивая загрузка + прогрев
  (`_ensure_voice`) при первом использовании каждого голоса.
- 22050 Hz, **моно** (NOT 48kHz/stereo, как было у MOSS).
- Текст нормализуется через `new_tts/ru_textnorm.py` (латиница→кириллица, F1-жаргон) ДО
  синтеза; предложения режутся на сегменты ≤90 символов (`_split_segments`).
- `synthesize_streaming()` (посегментная генерация) **используется**: `_play_blocking`
  зовёт `_play_streaming` (`voice/tts.py:665`), а тот — `synthesize_streaming` у
  Yandex либо у Piper. Прежняя запись здесь утверждала обратное («мёртвый код с
  до-Yandex архитектуры») и противоречила собственному бэклогу ниже, где Этап B
  (настоящий streaming playback) закрыт 2026-07-09. Исправлено при сверке
  2026-08-14; `YANDEX_TTS_STREAMING_PLAYBACK` — kill-switch этого пути.

**Yandex SpeechKit (`yandex_ai/speech.py` + `client.py` + `voices.py`):** REST/LPCM, голос
по персоне через `yandex_ai.voices.resolve(persona, overrides)`; ключ кэша — `y:{voice}|
{emotion}|{speed}` (`_voice_key`), отдельно от Piper-ключа (`piper:{persona}`) — фолбэк-звук
Piper никогда не попадает под Yandex-ключ (иначе почин ключа не вернул бы Yandex обратно).

### Голоса по персонам

Voice cloning **не реализован** — Piper клонирование не поддерживает (фича существовала
только для MOSS и была убрана вместе с ним, см. «Голосовые файлы» ниже). Персона = либо
фиксированный Piper-голос (`PERSONA_VOICE` выше), либо, при живом Yandex, голос из
`yandex_ai.voices.DEFAULT_PERSONA_VOICE` (+ пользовательские оверрайды).

### Путь воспроизведения (кэш)

```
say(text) → TTSQueue.enqueue(text)         # не дропает, ставит в очередь
  → TTSQueue._worker (фоновый поток)
    → _play_blocking(text)
         cache hit  → _play_wav(cache_path)   # soundfile.read → радио-эффект → sd.play/wait
         cache miss → _synthesize(text, persona)   # Yandex, при неудаче — Piper
              → _save_wav(audio, sr, save_path)    # «сухой» звук, PCM_16 через soundfile
              → _play_wav(save_path)
```

**Важно о WAV-кэше:** кэш хранит «сухой» (без радио-эффекта) **моно** PCM_16 через
`soundfile` — и Yandex, и Piper сейчас отдают mono (раньше MOSS был stereo/48kHz, теперь
не так). Радио-эффект (`voice/radio_fx.py`) накладывается заново при КАЖДОМ
воспроизведении — тоггл в настройках не портит и не требует инвалидации кэша.

### Воспроизведение

- Primary: `sounddevice` (`sd.play`/`sd.wait`)
- WAV чтение/запись: `soundfile`
- Fallback (sounddevice не установлен): `winsound.PlaySound`
- Fallback TTS (ни Yandex, ни Piper недоступны): `pyttsx3`

### TTS-кэш (voice/cache.py — `TTSCache`)

Добавлен для снижения задержки озвучки (запрос пользователя: "как у
gridfather.ai — near-zero latency", но строго офлайн/бесплатно).

- Ключ: `sha1(text + "|" + speaker)` → `DATA_DIR/tts_cache/<hash>.wav`
- WAV-файл кэша = файл воспроизведения, не временный (не удаляется)
- `evict_if_needed()` — LRU по mtime, лимиты `max_files=3000`, `max_mb=300`
- При старте — фоновый прогрев (`_prewarm_cache`): кэширует фразы из
  `templates.SIMPLE` без `{подстановок}` (старт, финиш, спид-трэп и т.п.)
  для текущего спикера
- Смена персоны в настройках → `engine.apply_settings()` → `voice.set_persona()`
  → следующие фразы озвучиваются другим спикером

**Подтверждено сквозным тестом:** повтор одинаковой фразы — 2.75с (генерация)
→ 0.0с (кэш-хит). 4 персоны → 4 разных файла/спикера. Повреждённый файл кэша
не валит приложение, перегенерируется на следующий запрос.

**Важный найденный и исправленный баг:** `tempfile.NamedTemporaryFile()` по
умолчанию создаёт файл на диске `C:` (системный TEMP), а кэш — на `G:`
(где лежит проект). `os.replace()` не может атомарно переносить файлы
между разными дисками Windows → кэш не работал до фикса. Решение:
`tempfile.NamedTemporaryFile(..., dir=os.path.dirname(final_path))` —
временный файл создаётся в той же папке, что и кэш, перенос становится
переносом в пределах одного диска.

## Известные gotchas и бэклог идей

Не привязано к конкретной сессии — общие ловушки и незакрытые идеи, которые стоит
знать ДО того, как трогать соответствующий код. Полный ход диагностики каждого пункта —
в `docs/CONTEXT_ARCHIVE.md`.

- **`bypass_speak_threshold=True` НЕ делает событие instant/critical — только
  `"priority": "critical"` даёт полный набор гарантий.** Найдено финальным сквозным
  ревью споттера (сессия 2026-07-20): `bypass_speak_threshold` освобождает ТОЛЬКО от
  `_muted_by_threshold`/`_is_stale_backlog_event` — двух гейтов, спроектированных для
  лёгких РЕПЛИК-КОМПАНЬОНОВ рядом с уже прозвучавшим critical-событием
  (`PIT_CALL_NOTICE`/`ENGINEER_GAP_DIGEST`). Он НЕ освобождает от: (1) per-code
  cooldown в `SessionGuard.should_emit()` (бустрапится только по `priority==
  "critical"`), (2) блокирующей паузы `MIN_COMMENT_GAP` (до 9с `time.sleep()`) в
  `_commentary_loop` (гейтится только по `importance >= PLAN_GAP_SKIP_THRESHOLD`,
  90), (3) `situation_dedup`/flashback-тишины (оба — `if priority != "critical"`),
  (4) настоящего ПРЕРЫВАНИЯ уже звучащей фразы (`voice_priority="critical"` только
  при `importance >= PLAN_INTERRUPT_THRESHOLD`). Для НАСТОЯЩЕЙ safety-реплики (не
  реплики-компаньона) нужен `"priority": "critical"` — `score_importance()` тогда
  флорит `importance` до `_CRITICAL_FLOOR=90` и это автоматически даёт все 4
  гарантии разом (тот же паттерн, что уже применён к `STRAT_BOX_CALL_*`). Если
  будущая фича заявляет «это безопасность, как PENA/box-call» — проверять именно
  `priority`, не только `bypass_speak_threshold`.
- **Пакеты F1 25/26 не в первый раз меняют раскладку по машинам после патчей игры.**
  Самые недавние случаи (сессии 06-28): (1) `parse_player_status`/`parse_player_telemetry`
  ошибочно добавляли `+1` к базе смещения — только `PacketParticipantsData` имеет
  префикс-байт `m_numActiveCars`, у остальных пакетов его НЕТ; (2) `PARTICIPANT_SIZE` был
  захардкожен в 60 байт, а F1 25 увеличил структуру (добавил данные ливреи) — каждая
  машина после первой читалась со сдвигом → мусорные имена/команды. Оба фикса теперь
  самокорректируются (шаг выводится из длины пакета), но если после патча игры снова
  появятся мусорные имена/шины — ПЕРВЫМ делом гонять `SPOTTER_DIAG=1 python app.pyw`
  (логирует stride + raceNumber/teamId по машинам), а не чинить парсер вслепую.
- **Спам комментатора — это переозвучка одной ситуации, а не повтор фраз.**
  `core/situation_dedup.py` (сигнатура: сторона+сосед+band дистанции, cooldown 20с) —
  рабочая заплатка. Корневая причина (рассинхрон триггер↔фраза: LLM пересказывает
  доминантную драму таймлайна на любой триггер, а не только на новый) НЕ решена
  полностью. Если спам вернётся в новой форме — решать привязкой фразы к конкретному
  триггеру, не ещё одним слоем дедупа поверх текущего.
  **07-04:** нашёлся ВТОРОЙ, независимый источник ощущения "говорит без остановки" —
  не повтор ситуации, а просто слишком частый каданс+бэклог: `MIN_COMMENT_GAP=4.0` +
  неограниченная `event_queue` без сброса устаревших некритичных событий. Пофикшено
  (`MIN_COMMENT_GAP=9.0`, `core/engine.py::_is_stale_backlog_event()`) — см. сессию
  2026-07-04. Если жалоба на спам вернётся снова — сначала проверить, это ситуация-
  дедуп (LLM про одно и то же) или снова каданс/бэклог (сплошной поток РАЗНЫХ фраз).
- **`sounddevice`: модульный `sd.play/wait/stop` нельзя мешать между потоками.**
  Эти функции делят один и тот же глобальный указатель стрима процесса. Если поток A
  вызывает `sd.play()` (создаёт новый стрим), а поток B в этот момент дёргает
  `sd.stop()` (напр. прерывание critical-приоритетной фразой) — гонка на нативном
  PortAudio/WASAPI-объекте, крашила процесс access violation'ом (0xc0000005 в
  `ntdll.dll`, см. сессию ниже). Фикс — выделенный `sd.OutputStream` на каждый вызов
  воспроизведения (`voice/tts.py::_play_wav`), опубликованный в `self._current_stream`
  под локом; `_interrupt_playback` зовёт `.abort()` именно на этот объект, не на
  модульный глобал. Тот же принцип уже был применён для записи микрофона —
  `voice/listener.py::_default_recorder` (комментарий в коде). Если где-то ещё
  появится прямой `sd.play/rec/wait/stop` — сразу подозревать этот же паттерн гонки.
- **OpenF1 сознательно НЕ используем как источник для живого комментария.** Отдаёт
  данные РЕАЛЬНЫХ гонок по `session_key`, а Spotter комментирует видеоигру (UDP из
  F1 25) — сопоставить игровую сессию с session_key реального GP нечем. Jolpica/Ergast
  (поиск по номеру машины/фамилии, не по session) — верный источник для комментария.
  Предложат снова — уже отклонили, см. архив (сессия 06-28). Real-F1 Benchmark — другой
  случай, см. следующий пункт.
- **Real-F1 Benchmark/секторы: маппинг трасс СВЕРЕН с живым API 2026-07-05 —
  OpenF1 разблокировался (401 снят), нашлись и исправлены 4 реальных расхождения.**
  `core/openf1_client.py::CIRCUIT_ID_TO_OPENF1_LOCATION` заполнялась по F1-знаниям без
  сверки (см. предыдущие сессии) — прямой запрос `GET /v1/sessions?year=2023..2025&
  session_name=Race` и сравнение distinct `location` показал: `villeneuve` (было
  `"Montreal"`, стало `"Montréal"` — диакритика), `interlagos` (было `"Sao Paulo"`,
  стало `"São Paulo"` — диакритика, риск был предсказан заранее и подтвердился),
  `marina_bay` (было `"Singapore"`, реально `"Marina Bay"`), `yas_marina` (было
  `"Yas Marina Circuit"`, реально `"Yas Island"`). `rodriguez`→`"Mexico City"`

  найдено: OpenF1 переименовал `Miami` → `"Miami Gardens"` начиная с сезона 2025 —
  единственный circuit_id, где имя меняется МЕЖДУ годами (остальные 23 стабильны на
  2023-2025) — добавлен `CIRCUIT_ID_OPENF1_LOCATION_ALIASES` + вторая попытка в
  `get_session_key()`, если основное имя не нашло сессию. Живой smoke после фикса:
  все 24 circuit_id резолвят `session_key` (2024 или 2025). 3 новых теста в
  `tests/test_openf1_client.py`. Закрывает «Открытые баги/задачи» #3.
- **Латиница от Jolpica для пилотов ВНЕ статического словаря — ЗАКРЫТО 2026-07-09.**
  См. сессию ниже.
- **Piper: неверное произношение НЕ всегда чинится текстовыми трюками.** Знак `+` и
  юникод-акцентные маркеры espeak игнорирует; кластер «свя…зи» звучит криво даже с
  фонетически верным переписыванием — это потолок акустической модели `medium`, не

- **"Ферстаппен" в Yandex TTS: РЕШЕНО 07-08 — дело было не в коде, а в кэше.**

**Закрыто 2026-08-14, вторым заходом (три из семи только что найденных):**

- **`interrupt_policy` — УДАЛЕНА, а не подключена.** Решение принято по факту:
  из четырёх её значений очередь реализует полтора (critical действительно
  прерывает, high/normal встают по рангу), а `replace` и `drop_if_busy` не
  делает НИКТО. То есть в логе стояло `policy=drop_if_busy` у реплики, которая
  спокойно ждала очереди за тремя другими. **Диагностика, показывающая не то,
  что происходит, хуже её отсутствия** — на ней и разбирают проды. Лог теперь
  печатает `category`, то есть ровно то, чем очередь и решает. Замысел сохранён
  комментарием в шапке `policy.py`, чтобы не изобретать заново; `REPLACEABLE_
  CATEGORIES` оставлен как знание о предмете.
  **Пять тестов на эту политику удалены, и это отдельный урок:**
  `test_low_is_dropped_when_radio_is_busy` и

  согласованность выдумки с самой собой, зелен ровно до тех пор, пока никто не
  сверит его с продуктом.
- **Сироты-скриншоты** — `storage.prune_screenshots()` зовётся сразу после
  `prune_sessions` (порядок важен: снимки только что удалённых сессий обязаны
  попасть под чистку тем же проходом). Считает от ЖИВЫХ ссылок, а не от
  возраста: снимок годовалой сессии, ещё лежащей в архиве, сохраняется, а
  вчерашней удалённой — нет. Отсрочка `SCREENSHOT_GRACE_S` закрывает разрыв
  между асинхронным снимком и публикацией поста. Нечитаемая база означает
  «набор ссылок неизвестен» и отменяет чистку целиком: удалить лишнее хуже, чем
  оставить лишнее.
- **`game_sessions/` не чистится** — `archive.prune_game_sessions()` после
  финиша, в фоне. **Наивное «оставить N свежих» здесь ломало бы продукт**, и это
  главное в функции: архив — карьерная ПАМЯТЬ, по нему коуч ищет эталон трассы
  и прошлый разбор. Рекорд Монцы может лежать в заезде полугодовой давности, и
  удалить его значит молча откатить цель коуча к более медленному кругу.
  Защищаются три множества: последние N, лучший эталон ПО КАЖДОЙ трассе и
  свежайший разбор по каждой трассе. Порог 200 намеренно щедрый — задача
  ограничить безграничный рост, а не подстричь архив: при 88 заездах и 394 КБ
  чистка не сработает вовсе, а начнёт работать там, где появилась цена

**2026-08-26 (продолжение) — коуч за весь архив не сказал бы ни слова.**

Задача звучала «откалибровать пороги коуча по архиву, чтобы включить его по
умолчанию». Счёт показал, что калибровать нечего: воронка пуста не в конце, а
по всей длине.

    22 срыва в картах архива (30 заездов, 152 круга)
    −3  машина стоит (гейт MIN_MOVING_KMH, архив писался до него)
    −2  длиннее MAX_EVENT_DURATION_S
    =17 прошли бы сегодняшний детектор — 0.11 на круг
     9  с привязкой к повороту (52%)
     8  групп «трасса + поворот + вид», максимальный размер 2
     0  прошло порог повтора 3

**За весь архив коуч не мог произнести ни одного урока.** Это не «пороги
немного не те», это пустая воронка.

**Порог повтора — не связывающее ограничение,** и это главный вывод для
планирования: снижение до 2 даёт 1 урок на 152 круга, счёт по повороту вместо
вида — тоже 1 (Монреаль, поворот 4: oversteer, wheelspin и offtrack по разу).
Менять правило группировки ради одного урока на полторы сотни кругов — правка
с нулевым эффектом и ненулевым риском. Решение: **не трогать**.

**Половина найденного теряется на дырах в картах, и это доказано скоростью.**
Из 8 срывов без привязки 5 случились на 63–131 км/ч, все на Майами. На прямой
так не едут: значит `phase: straight` там — не прямая, а участок, которого нет
в карте (Майами: 56% круга, 13 поворотов из 19, крупнейшая дыра 1402 м).
Прежняя формулировка «41% с corner_id null из-за дыр в картах» подтвердилась,
но теперь у неё есть довод, а не догадка.

**Чего архив не умеет — и почему это не тупик.** Сколько раз сигнал НЕ дотянул
до порога, в архиве не видно ни при каких вычислениях: туда попадает только
найденное. Ровно на этот вопрос заведён полевой журнал — `field_log.observe`
копит распределения с порогами ИЗ МОДУЛЯ ДЕТЕКТОРА, `flush_stats` сбрасывает
их раз в круг, а `diag_report` печатает «порог взят N раз» и отдельно случай
«не взят ни разу». Цепочка проверена целиком и работает: один заезд с
`SPOTTER_DIAG=1` закрывает вопрос.

Попутно: `observe()` сперва показался невызванным (греп по `.observe(` его не
нашёл) — на деле он зовётся через алиас `observe = self._field.observe` в
`engine.py:2038`. Греп по имени метода не находит вызовов через локальную
переменную; проверять надо по имени поля тоже.

остаток светит непрозрачным `OVERLAY_BACKGROUND` поверх трассы (тот самый
серый кусок); где выше — низ реплики режется, и чаще всего это комментатор:
его текст пишет LLM, потолка в 18 слов, как у инженерского банка, у неё нет.

Происхождение: до 08-25 окно было `430x178`, коммит 6397b70 сменил его на 108,
чтобы убрать «хвост» в 70 px. Хвост убрался вместе с запасом на длинную
реплику. **Тот же класс, что COLL в шестой таблице:** правильное решение
принято один раз и не пройдено по соседям.

Механизм слежения за карточкой в коде УЖЕ БЫЛ (`_content_size_from_shapes` →
`_target_for`), и в этом соль: он считал ГАБАРИТ фигуры (`h`), а не её дальний
край (`y + h`). На входе и выходе карточка смещена на `MOTION.enterShiftPx`,
и окно оказывалось на этот сдвиг короче содержимого. Правка — одна строка;
цену имеет тест: `_RADIO_CARD_STATES` держит все девять замеров разом, а не
один случай, как прежний тест на 134 px.

**Вторая: `engineer_character` доезжал до голоса и до слов, но не до подписи.**
Нашлась сухим прогоном (см. ниже) на настройках пользователя
(`persona=toxic`, `engineer_character=grom`): в наушниках говорит Гром своим
голосом и своим пулом формулировок, а карточка на каждой реплике подписана
«ИГОРЬ ВОЛКОВ» с его инициалами и портретом. Причина — два списка имён:
`speakers.RACE_ENGINEER` (фиксированный) и `voice_cast.CHARACTERS`
(персонажи). `profile_for` знал только первый.

Правка: профиль инженера выводится из `voice_cast` (`_engineer_profile`), а
`character` протянут через `to_ui_dict` и `RadioSession` тем же приёмом, что
персона — отдельным провайдером (`set_character_provider` в `web_server`).
Роль, акцент и `speaker_id` общие: меняется человек, а не должность. **Пол
едет вместе с именем** — иначе вернулся бы баг «ЛЕВ ТИХОНОВ женским голосом»,
уже доезжавший до живой гонки, но с Соколовой.

Проводку проверяют два теста поверх юнитов: выбор обязан доехать и до
активного сообщения, и до справочника `speakers`, по которому UI подписывает
«слушаю» ещё до появления реплики. Пять тестовых заглушек `radio_session`
пришлось дописать — и это правильный сигнал: они падают, когда проводку
забыли.

**Инструмент: `tools/rehearse.py` — сухой прогон гонки без F1 25.**
Сценарий из 18 реплик прогоняется через настоящие `policy` / `phrases` /
`voice_cast` / `address` и печатает транскрипт: круг, канал, срочность, имя в
кадре, голос, число слов, текст. Ключи: `--persona`, `--character`, `--short`,
`--diff` (сравнение с прошлым транскриптом), `--out`.

Что он проверяет: банк формулировок, раздачу каналов, раздачу голосов,
обращение по имени, потолки длины. Чего НЕ проверяет и не может: парсер
пакетов, детекторы срывов, пороги — им нужна телеметрия. Зелёный прогон не
означает удачного заезда, он означает, что произнесённый текст будет таким.

**Третья находка того же прогона, закрыта в этом же заходе: код в эфире.**
`commentator/templates.py::render` последним резервом возвращал
`event.get("description", code)` — то есть на коде без пула и без описания в
эфир уходил САМ КОД (`render({'event_code': 'ZZZZ'})` → `'ZZZZ'`, проверено
прямым вызовом). Инженерский банк в такой же ситуации отказывает и молчит
(«лучше промолчать, чем произнести строку с фигурными скобками»), а
комментаторский произносил служебную строку: две противоположные политики на
один и тот же отказ в одном приложении.

По решению пользователя резерв теперь — описание, а при его отсутствии
ТИШИНА плюс `WARNING` в лог. Пустая строка здесь не потеря: по всему пути
генерации она уже означает «сказать нечего» (`brain._render_template` не
запишет её в память, вызывающий положит событие в ленту как `muted`).
Описание не тронуто: `EVENT_DESCRIPTIONS` держит русские читаемые строки, и
заменить их тишиной значило бы лечить симптом ампутацией.

Почему WARNING обязателен: пул отсутствует ровно тогда, когда новый
`event_code` завели и не прошли по всем per-code таблицам — тот самый
многократный случай этого проекта. Без строки в логе тишина спрятала бы
причину до следующего живого заезда.

**2026-08-25 (продолжение) — старт с решётки был не поломкой сигнала.**

Заход начался с вопроса «можно ли вытащить что-то ещё из уже проеханного», и
ответ оказался дороже вопроса: **диагноз 08-15 был неверен, а стоил он живого
заезда.**

Запись гласила: пики `wheelspin` = 5.4 при собственном потолке достоверности
`SANE_MAX_SLIP_RATIO = 3.0`, значит сигнал недостоверен, значит надо проверять
раскладку пакета 13 живым заездом с `SPOTTER_DIAG=1`, и только потом трогать
пороги. Свод ВСЕХ срывов архива (а не выборки по одной трассе) показал другое:

    kind           peak  speed   поворот
    wheelspin     5.417      0   Turn 1
    wheelspin     5.402      0   Turn 1
    wheelspin     5.386      0   Turn 1
    wheelspin     0.415     56   Turn 4
    wheelspin     0.266     49   Turn 10

Все три «невозможных» пика — при нулевой скорости на первом круге в первом
повороте. Это старт с решётки трёх разных гонок. Проскальзывание считается как
(скорость колеса − скорость земли) / скорость земли; на старте знаменатель
около нуля, и величина взлетает. **Арифметика, а не сбитый офсет.**

**Что делает ошибку поучительной:** гейт по движению в проекте БЫЛ — в
`health.py`, с прямым объяснением («нули стоящей машины — правда, а не
поломка»). До детектора его не довели, и `speed_kmh` в `slip.py` только
записывался, ни разу не участвуя в решении. Тот же класс, что `COLL` в шестой
таблице и `PIT_EXIT` мимо множества из одиннадцати кодов: правильное решение
принято один раз и не пройдено по соседям.

**Вторая половина урока — про метод.** Разбор 08-15 шёл по выборке (три заезда
Майами) и по агрегату (пик, доля вне поворота). Ни то, ни другое не показывает
`speed_kmh` рядом с пиком — а именно эта колонка всё и объясняла. Число,
объявленное невозможным, стоит сначала посмотреть в его собственной строке.

Правка: `MIN_MOVING_KMH` переехал в `slip.py` (владелец один на два модуля),
кадры ниже порога не открывают срывов, но УЖЕ открытые закрываются штатно —
разворот гасит скорость, и занос, начавшийся на 180 км/ч, обязан доехать до
урока. Отсутствие скорости в кадре считается движением: «данных нет» и «машина
стоит» — разные ответы, и подменять первый вторым значило бы выключить коуча
на источнике без этого поля и не сказать ни слова.

Проверено не только тестами: все пять архивных `wheelspin` прогнаны через
детектор заново — три артефакта старта отсеяны, оба настоящих (49 и 56 км/ч)
остались.

**Что ещё вытащилось из тех же файлов:**

  survey_track.py montreal` читает его прямо сейчас: промер 30 поворотов против

  повороте читаются как «закономерности нет». Формально дисциплина верная —

**2026-08-14 — карты трасс: сделан ИЗМЕРИТЕЛЬ, а не карты.**
Задача звучала «доделать карты», но доделать их кодом нельзя, и это не отговорка,
а то самое правило, которым сама задача и снабжена: доли поворотов берутся только
измерением по своей телеметрии, потому что по этой карте коуч судит о пилотаже —
выдуманная доля даёт уверенно неверный совет, что хуже молчания. Внешнего

входные данные (см. соседний открытый пункт).

Поэтому дописано то, чего не хватало для измерения, — и после этого карты
доделываются одним заездом на трассу.

`core/track_ai/survey.py`. Меряет по `yaw_rate` из MotionEx, а не по рулю: боковое
ускорение (a = ω·v) — это ФАКТ поворота, руль же можно крутить и на прямой. Апекс
= точка минимума скорости внутри дуги, тип — по измеренной апексной скорости,
направление — по знаку. Тесты строят синтетический круг с заранее известными
поворотами: на живой телеметрии правильный ответ неизвестен, ради него всё и
затевалось.

**Тест поймал настоящий дефект алгоритма.** Первая версия группировала кадры
только по разрыву дистанции, и шикана склеивалась в ОДИН поворот: обе дуги идут
вплотную и обе выше порога. Знаковая сумма при этом взаимно гасилась — связка
получала направление более длинной дуги и апекс МЕЖДУ дугами, то есть коуч назвал
бы место, которого нет. Группа теперь рвётся и по смене знака: перекладка — это
всегда новая дуга.

Проводка: промер кормится из `_coach_tick` тем же кадром, что детекторы, и
разбирается на завершении круга. Сохраняется ЛУЧШИЙ круг сессии по покрытию (один
смазанный не должен затирать удачный), пит-круги не участвуют. Планка лучшего
покрытия сбрасывается на смене трассы и сессии — без этого первый круг на новой
трассе не сохранился бы вовсе, если на прошлой покрытие было выше (тот же класс
бага, что три находки утреннего ревью).

**Карта сама не меняется.** Промер уезжает в `DATA_DIR/track_survey/` и в
`tracks/` не подставляется: разметку правит человек через
`scripts/survey_track.py`, глядя на дифф (СОВПАЛ / СДВИНУТ / НОВЫЙ / ПРОПАЛ).
Автоподмена означала бы совет, который пилот не может ни предсказать, ни
проверить, и один грязный круг переписывал бы всю трассу. `ПРОПАЛ` намеренно не
значит «удалить»: пологий поворот проходится без заметного бокового ускорения.

Проверено сквозным прогоном на синтетическом промере Сузуки: 18 против 14 в
карте, четыре помечены НОВЫЙ, совпадения сошлись доля в долю.

**2026-08-11 — разбор живой гонки: 9 багов из логов, закрыты первые три.**
Материал — `spotter.log` (342 КБ) за реальный заезд плюс архив 49 сессий. Общий урок:
все три бага были *между* корректными модулями, ни один не ловился юнит-тестом.

(1) **Токены позднего связывания доезжали до пользователя.** `RadioMessage.with_phrase()`
существовал и был покрыт тестом, но в проде его не звал НИКТО (`grep with_phrase`
находил только определение, комментарии и тесты). Резолв `resolve_for_playback()`
уезжал в TTS и терялся: голос называл число, а в карточке рации оставалось
`{gap}`/`{ers}`, включая поле `repeatable` («повтори» читало шаблон). Фикс — привязка
текста в `_note_radio_state(..., phrase=...)`: снимок в `_radio_lifecycle` канонический,
все последующие переходы (playing/completed) читают его, поэтому связывать надо ОДИН
раз и именно там. Немой путь (`should_voice=False`) чинится отдельной строкой — он идёт
мимо `_make_prepare`. Правило на будущее: тест «резолвер вызван» ≠ тест «резолв доехал»;
проверять `to_ui_dict()` целиком через `json.dumps`, а не возврат функции.

(2) **Пол голоса не был связан с полом имени в кадре.** Персона `calm` подписана
«ЛЕВ ТИХОНОВ», а голос имела `marina` — женский. Имя живёт в `core/radio/speakers.py`,
голос в `yandex_ai/voices.py`, по отдельности обе константы выглядят верными. Заведена
`voices.VOICE_GENDER` + `gender_of()`, поле `gender` у `SpeakerProfile` и
`EngineerCharacter`, `_first_free()` фильтрует по полу. `calm` переведена на
`alexander`. Побочно закрыта «известная слабость каста», которая была ЗАКРЕПЛЕНА
тестом как приемлемая: Соколова (единственный женский персонаж) теряла `marina`
комментатору и звучала мужским запасным — теперь у неё ровно один голос, и занятость
даёт громкий `VoiceCastError` вместо тихой подмены. Инвариант «≥2 голоса у персонажа»
переформулирован: считать надо голоса СВОЕГО пола (м — 2, ж — 1), потому что
комментатор всегда мужской. Осторожно: тест покрытия `_V1_VOICE_FALLBACK` брал набор
только из `DEFAULT_PERSONA_VOICE` и работал случайно — голоса приезжают и через
оверрайды каста; непокрытый премиальный голос на пути v1 = HTTP 400 = тишина.

(3) **Таймаут v3 платила каждая фраза.** В логе 13 подряд `future timeout (15s)`, после
каждого — откат на v1, который подменяет премиальный голос легаси-аналогом
(`_V1_VOICE_FALLBACK`: alexander→filipp, marina→alena). Отсюда жалоба «весь заезд
насиловали голову разными голосами»: тембр менялся пофразно, в зависимости от того,
ответила v3 или нет. Худший случай был 6 (GigaChat) + 15 (v3) + 6 (v1) = 27 секунд до
звука. Сделано: `YANDEX_TTS_V3_TOTAL_TIMEOUT` 14→9, `YANDEX_TTS_TOTAL_TIMEOUT` 5→4 и
предохранитель на v3 (`YANDEX_TTS_V3_FAILURE_THRESHOLD=3`,
`YANDEX_TTS_V3_BREAKER_COOLDOWN=120`): после трёх неудач подряд сессия целиком уходит
на v1 и не трогает v3 до остывания. Стабильность тембра здесь — не побочный эффект, а
вторая цель: пока цепь разомкнута, все реплики идут одним маршрутом. Часы монотонные.

`packets.py::CRITICAL_EVENTS`, поэтому ЛЮБОЕ касание идёт к LLM как критическое и даёт
«ХАОС НА ТРАССЕ» (градация есть, но только у инженера: порог 20 / критично 70; образец
правильного поведения — `racefeed/engine.py::candidates_deferred`, который ждёт
подтверждённого последствия); щуп по форме окна рации («обрубок» под карточкой);

играя за Леклера пользователь становился Расселлом; смещение `raceNumber` выбирается по
ненадёжному `packet_format>=2026`, у `teamId` для этого уже есть аварийный словарь
`_SEASON_PACK_V124_TEAM_IDS`, у номера — нет; нужен дамп `SPOTTER_DIAG=1`); коуч молчит,

**2026-08-11 — пункт 1: градация контакта вместо «ХАОСА НА ТРАССЕ».**
Корень был не в промпте и не в персоне, а в одной строке: `COLL` безусловно лежал в
`packets.py::CRITICAL_EVENTS`. Игра шлёт COLL на ЛЮБОЕ касание и тяжести не сообщает
вовсе, поэтому каждое притирание получало `priority=critical` → важность 90+ (пол
`_CRITICAL_FLOOR`) и директиву LLM `"авария"` (`planner.py::_REACTION_BY_CODE`).
Драматизировал не LLM — ему так велели.

Сделано: тяжесть выводится из ПОСЛЕДСТВИЯ. `_defer_contact` откладывает COLL игрока на
`_CONTACT_WINDOW_S=2.5` (у RaceFeed окно 30 с — ленте можно ждать, живому голосу нет),
`_grade_contact` смотрит ПРИРОСТ повреждений и потерю позиции, публикует
`COLL_LIGHT` / `COLL` / `COLL_HEAVY` (важность 45 / 85 / 100, директивы «лёгкое
касание» / «контакт» / «авария»). Прирост, а не абсолют: разбитое кругом раньше крыло
не должно делать сегодняшнюю притирку аварией. Повторный контакт внутри окна продлевает
его, а не заводит вторую реплику. Флаг `contact_graded` уезжает в namespace
`event["radio"]` (`plumbing.attach`) — оттуда он не попадёт ни в facts для LLM, ни в
отпечаток RaceFeed, и он же не даёт оценке уйти на второй круг.

Два урока, оба стоили бы времени позже:
(1) **Низкой важности НЕ достаточно для тишины.** Порога озвучки по важности в проекте
нет вовсе — `_should_voice` пропускает всё, кроме выключенного автоголоса; важность

### Сессия 2026-08-11 (продолжение) — Отчёт диагностики: заезд в одном сообщении

Запрос: сделать логи так, чтобы состояние приложения читалось ОДНИМ сообщением.
Полевой журнал на это уже отвечал по содержанию и не отвечал по форме — двадцать
кругов дают тысячи строк JSONL, и «пришлите лог» перестаёт быть действием,
которое можно выполнить.

**Досчитано то, чего в журнале не было: перепись пакетов.** Счётчик в адаптерах
телеметрии считает пакеты ПО НОМЕРУ, до всякого разбора, движок сбрасывает его в
журнал раз в круг. Без этого «пакет 13 не приходит» и «пакет 13 приходит, но
парсер отдаёт нули» неотличимы — а починки у них разные: настройки игры против
офсетов. Туда же ушла запись про трассу с переписью типов поворотов: без
разметки коуч не назовёт место, и по молчанию это выглядит как «ошибок не было».

**`core/diag_report.py` — журнал в десять проверок с вердиктом.** Окружение,
пакеты, трасса, сигнал коуча, срывы, эталон, работа сессии, положение в поле,
причины молчания, ошибки лога. Чистый модуль: на входе разобранные записи, на
выходе текст, никакого I/O — поэтому каждая проверка стоит на питоновском тесте
с синтетическим журналом, а не на живом заезде.

**Третий вердикт обязателен.** Рядом с «ОК» и «ПРОБЛЕМА» у каждой проверки есть
«НЕТ ДАННЫХ», и это не формальность: «коуч молчал, потому что сигнала не было» и
«коуч молчал, потому что порог не взят» требуют противоположных действий, а
раздел без третьего состояния их не различает. Там, где различить нельзя изнутри
(чистый заезд против завышенного порога), отчёт называет ОБА варианта, а не
выбирает один наугад.

**iRacing — отдельный случай, а не сломанный UDP.** Совет «включите UDP в F1 25»
пользователю iRacing бесполезен; перепись там ведётся под синтетическим ключом, и
отчёт прямо говорит, что на этом источнике не работают коуч, «Гараж» и положение
в поле. (Та же поправка нужна формулировке в `coach_ai/health.py` — не сделана,
см. ниже.)

**Размер под сообщение — под тестом.** `test_the_report_stays_small_enough_to_paste`
кормит отчёт тысячей записей и требует меньше 120 строк на выходе. Отчёт, который
не влезает в сообщение, повторяет судьбу журнала, который он сжимает.

**`tools/diagnose.py`** находит свежий журнал сам (корень, `DATA_DIR`, `dist/`),
читает хвост `spotter.log` на ошибки, печатает отчёт и кладёт рядом
`spotter-diagnostic-<дата>.txt`. Консоль принудительно переводится в UTF-8 с
`errors="replace"`: унаследованная консоль Windows отдаёт cp866, и `print()`
русского текста в ней падает с `UnicodeEncodeError` — то есть диагностика
обрывалась бы на первой строке. Инструкция — в README отдельным разделом.

**Проверено:** полный `pytest` — 4807 тестов, 0 падений (30 новых в
`test_diag_report`). Генератор прогнан не на синтетике, а на журнале, записанном
НАСТОЯЩИМ `FieldLog` с настоящими порогами `slip.py`: отчёт верно нашёл три
проблемы из подстроенных (нет пакета 5, сигнал ниже порогов, эталон без
отклонений) и верно промолчал про остальное.

**Не сделано:** формулировка «включите UDP, формат 2025» в состоянии коуча
по-прежнему не смотрит на `telemetry_source` — на iRacing она вводит в
заблуждение. В отчёте этот случай разведён, в приложении ещё нет.

### Сессия 2026-08-11 — Коуч объясняет сам себя + тип поворота как причина

Доводка коуча до релизного состояния. Две вещи, каждая закрывает свой класс
претензий.

**Коуч не объяснял сам себя — и это была та самая исходная жалоба.** «Бесполезная
функция, ничего не даёт» при ВКЛЮЧЁННОМ тумблере. Разобраться было нечем:
молчащий коуч выглядит одинаково при выключенном тумблере, при неповторяющейся
ошибке, при не доехавшей телеметрии движения и при завышенном пороге детектора.
Четыре разных диагноза с четырьмя разными действиями — и ни одного способа их
различить, кроме чтения кода.

`core/coach_ai/health.py` отвечает на это одной строкой на экране. **Это не
полевой журнал:** тот пишет распределения на диск, живёт за `SPOTTER_DIAG=1` и
адресован тому, кто чинит пороги; здесь — короткий ответ пилоту, всегда
включённый.

**Все причины молчания сведены в ОДНУ точку** — `engine._coach_silent()`.
Раньше причина уезжала только в журнал (десять вызовов `_field.record`), то есть
была видна разработчику и не видна пилоту никогда. Теперь один вызов кормит и
журнал, и экран: разойтись они не могут по построению. На связку стоит сторож —
тест сканирует `engine.py` на ключи `_coach_silent` и падает, если у нового
ключа нет человеческой формулировки.

**Порядок проверок — это порядок ДЕЙСТВИЙ пилота:** сначала то, что чинится в
настройках игры, потом в настройках приложения, и только потом за рулём. Поэтому
сломанный поток данных бьёт выключенный тумблер, а не наоборот.

**Порядок колёс проверяется без руля, и это главное для релиза.** Прежний блокер
дефолта — «перепутав порядок `RL, RR, FL, FR`, коуч уверенно называл бы не то
колесо» — требовал живого заезда. Оказалось, есть проверка, которой заезд не
нужен: **формула заднеприводная, и передние колёса под газом буксовать НЕ МОГУТ,
они ничем не приводятся.** Если под сильным газом (без тормоза) положительное
проскальзывание систематически больше на передних — пары переставлены. Сигнал
`swapped`, и он старше тумблера по рангу: коуч, называющий не то колесо, —
проблема выше уровнем, чем коуч выключенный.

**Тип поворота — та причинная модель, которой не хватило фазе 3.** Разметка
(`slow/medium/fast/chicane/hairpin`, 325 поворотов на 24 трассах) лежала в
`tracks/*.json` с самого начала и работала только на споттера. Разница
принципиальная: «теряешь в седьмом» — это техника, «теряешь во ВСЕХ медленных» —
подпись машины, одинаковая проблема в непохожих местах трассы техникой не
объясняется.

Отсюда единственный новый вывод по гаражу, зато учебниковый: **прижимная сила
растёт с квадратом скорости**, поэтому снос на медленных поворотах указывает на
механический баланс, а на быстрых — на аэродинамический. Это физика, а не
догадка. `medium` сознательно вне разбора: там работают оба механизма сразу, и
разделить их нельзя — молчание честнее любого из двух ответов. **Чисел
по-прежнему не называем:** величина зависит от трассы и от того, что уже стоит в
сетапе, и ограничение фазы 3 здесь остаётся в силе.

**Считаются ПОВОРОТЫ, а не срывы.** Пять сносов в одной шпильке — это одна
шпилька, а не механический баланс. Ровно на этой подмене строится большинство
ложных советов по сетапу, и на неё стоит отдельный тест.

**Снова падеж, снова найден чтением вывода.** Один словарь названий типов
обслуживал две конструкции и давал «в 3 из 4 медленных ПОВОРОТАХ» вместо
«поворотов». Тесты проверяли подстроку «3 из 4» и проходили. Теперь два словаря:
именительный для заголовка строки на экране, родительный для счётного оборота.

**Проверено:** полный `pytest` — 4777 тестов, 0 падений (по этой работе 26 в
`test_coach_health`, 6 в `test_coach_health_wiring`, 16 в
`test_coach_corner_types`, 2 в гараже). `tsc --noEmit` и production build чистые,
`webui/` пересобран (robocopy exit 3). Блоки подняты на данных настоящих модулей
тем же приёмом (временная страница → build → чтение HTML → удаление): «ПОЧЕМУ
МОЛЧИТ» с живой формулировкой, разрез по типам поворотов, вывод про баланс в
«Гараже».

**Дефолт `driving_coach_enabled` НЕ трогал.** Решение «менять только после
чистого круга» принадлежит пользователю, и отменять его молча нельзя. Но блокер
сменил форму: проверка порядка колёс больше не требует ручного разбора
`SPOTTER_DIAG`, а любой отказ теперь виден на экране словами, а не молчанием.

**Параллельная сессия** в это же время правила оверлей (чернота, форма окна) —
её файлы не трогал, её запись ниже.

### Сессия 2026-08-10 — Оверлей: чернота, форма окна и выключатель виджетов

**Окно теперь обрезается по форме виджета — прозрачность не понадобилась.**
Годами считалось, что раз WebView2 на этом хосте не отдаёт альфу на десктоп, то
чёрный прямоугольник вокруг круглого радара неизбежен (из-за этого в вёрстке
были запрещены скругления, срезы и тени). Верно только про АЛЬФУ: регион окна
(`SetWindowRgn`) работает и на layered-окне WebView2. Замерено на живом окне,
четыре точки экрана: без региона углы принадлежат окну, с эллипсом — уходят
рабочему столу, середина остаётся. **Снимать `WS_EX_LAYERED` при этом нельзя —
окно пропадает целиком** (тоже замерено). И ещё: снять регион и поставить
заново на том же окне гасит его — регион всегда ЗАМЕНЯТЬ, а не сбрасывать.

**Форму сообщает страница, ИЗМЕРЯЯ свою вёрстку** (`data-overlay-shape` →
`getBoundingClientRect` + вычисленный `border-radius` → примитивы в базовых
координатах → `core/overlay_shape.py` масштабирует под окно). Список чисел на
стороне Python разъехался бы с CSS молча: форма зависит от темы (фаска, радиус
карточки рации) и от состояния. Масштаб берётся из РЕАЛЬНОГО окна, а не из
сохранённого множителя — окно дополнительно зажимается клиентской областью игры.

**Гоча pywebview, которая стоила бы всей фичи:** объект `js_api` обходится
рекурсивно по всем ПУБЛИЧНЫМ атрибутам, чтобы выставить их методы в JS
(`webview/util.py::get_functions`). Ссылка на контроллер с публичным именем
увела обход в объектный граф WinForms и упала на «maximum recursion depth
exceeded». Держать такие ссылки под подчёркиванием. Юнит-тесты этого не ловили:
в них у окна нет `.native`. Поймал живой щуп.

**Пустые виджеты больше не занимают экран.** Окно рации в покое рисовало тёмную
карточку поверх игры всегда (`RadioPanel` возвращает `null`, но коробка `Widget`
была залита `PANEL`), радар без соседей висел тусклым кругом. Правило видимости
знает только страница — она же его и сообщает; в превью главного окна это
правило работало и раньше, теперь оно же применяется к отдельным окнам.

**Выключатель виджета** — `enabled` в `overlay_layout/<widget>.json` (мержится,
как позиция и размер; в файле остаётся только выключение). Выключенный виджет НЕ
поднимается как процесс: на машине, которая тянет F1 25, это и есть смысл.
Живо, без перезапуска: `OverlayProcessController` получил супервизор по mtime.
**Смещение порта считается от места виджета в `HUD_WIDGETS`, а не от позиции
среди запущенных** — иначе пропуск выключенного сдвинул бы порты соседей и
Ctrl+Alt+O уходил бы не в те окна.

**Проверено живьём, а не только тестами:** все восемь виджетов на 0.6 и 2.0
получают окно `base × scale`; настоящая страница присылает форму (таблетка —
две скруглённых коробки, радар — эллипс 24/252, панель с фаской — полигон);
у таблетки углы окна отданы игре, середина — виджету; радар и рация без данных
сообщают «показывать нечего», и окно скрыто.

### Сессия 2026-08-11 — Положение в поле по секторам + «во втором»

Заход начинался как поиск точек роста. Нашлось, что данные `Session History`
(пакет 11) — лучшие секторы КАЖДОЙ из 22 машин — лежат в движке с 2026-07-20 и
почти не работают. По дороге нашёлся дефект крупнее самой фичи.

**Поправка к собственному анализу, записана намеренно.** Сначала я заявил, что
сравнение секторов живьём не используется вообще. Неверно: `compare_best_sectors`
(`core/strategy_ai/sector_comparison.py`) звучит в сводке по разрывам. Но —
только с ОДНИМ ближайшим соперником и только в гонке. Разница между «ты на три
десятых медленнее соседа» и «твой второй сектор седьмой из семи» — это разница
между фактом и диагнозом: первое зависит от того, кто случайно едет рядом.

**Главная находка — «в втором повороте», и она не про секторы.** Коуч говорил
так на ВСЕХ четырёх фазах, на каждой трассе календаря, с момента появления
номеров поворотов. Дефект живёт на СТЫКЕ: шаблон банка держит предлог
(«в {corner_no} повороте»), числительное приезжает подстановкой из
`corner_words.py`, и ни одна из сторон не видит другую — поэтому ни одна не может
исправить стык сама. Ни один тест банка такое не ловил: все они проверяют
шаблоны и значения по отдельности.

`core/radio/euphony.py` — правило одно, вызывающих двое: `phrases.render()` (весь
банк) и `sector_comparison.py` (строка идёт в эфир МИМО банка). Область узкая
намеренно: полное правило беглого гласного требует фонетики («во Франции», но
«в фарватере»), а порождающий случай у нас ровно один — предлог перед словом на
«вт»/«вс». Неверное «во» слышно так же плохо, как неверное «в».

**Ещё три дефекта в той же живой строке сравнения секторов.** Она звучала как
«Ты быстрее Ландо Норрис в 1-м секторе на одна целая ноль десятых с»: полное имя
вместо фамилии, именительный падеж после «быстрее», цифровое порядковое и
величина, которую `num_to_words` разворачивал в «ноль целых ноль десятых с».
Причина одна на все четыре: **строка идёт в эфир мимо банка, и ни одна защита
банка на неё не распространяется** — ни тест на падежи имён, ни запрет цифровых
порядковых. Прежние тесты фиксировали сломанный текст как правильный результат.
Теперь правила соблюдаются вручную, и на каждое стоит свой тест; это записано в
шапке модуля, чтобы следующая правка не потеряла причину.

**`core/sector_standing.py` — место в поле по каждому сектору**, отрыв до лучшего
и кто его держит. Ключевое решение: **слабейший сектор выбирается по ОТРЫВУ, а не
по месту.** Восемнадцатое место с отрывом в сотую и третье с отрывом в полсекунды
требуют разного, и работать надо там, где лежит время. Порог отрыва равен порогу
произносимого (`num_to_words.MIN_SPOKEN_MS`): показывать на экране то, о чём эфир
сказать не может, — расхождение на ровном месте.

**Звучит в квалификации и практике — в отличие от сводки по разрывам.** У той
стоит `session_type != "race"` → выход, и раскладка, унаследовав тот же гейт,
оказалась бы бесполезной ровно там, где нужнее всего: в квалификации пилот весь
заезд занят поиском своего медленного сектора. Гейт остался только на
`engineer_chatter_enabled` — это информация инженера, а не коучинг.

**Отдельная секция `field_pace`, а НЕ поле внутри `coach_ai`.** Коуч отвечает
«где ты теряешь относительно СЕБЯ» с разрешением до поворота и причины; здесь —
«относительно НИХ», и разрешение грубее, сектор. Первое лечится техникой, второе
бывает и вопросом машины. Сложить два разных вопроса в один ключ значит
гарантировать путаницу на экране.

**Хвалим только за первое место в поле.** «Ты четвёртый в секторе, и это твоя
сильная сторона» — утешение, а не обратная связь. Слабое место при этом бьёт
сильное: подтверждение без работы уместно, работа, отложенная ради похвалы, — нет.

**Имя лидера сектора — только на экране.** В эфир оно потребовало бы падежа, а
падеж свободной строкой банк не выражает (та же причина, по которой чинилась
строка сравнения). На экране его читают глазами.

**Проверено:** полный `pytest` — 4701 тест, 0 падений (по этой работе 16 в
`test_sector_standing`, 14 в `test_field_pace_wiring`, 13 в `test_radio_euphony`,
переписан `test_sector_comparison`). `tsc --noEmit` и production build чистые,
`webui/` пересобран (robocopy exit 3). Блок «В поле» поднят на данных настоящего
модуля тем же приёмом, что и «Урок»: временная страница → production build →
чтение готового HTML, страница удалена, `webui/` пересобран начисто. Реплики
прочитаны глазами: «Во втором секторе ты седьмой в поле, лучший быстрее на
1,2 секунды».

**Не сделано:** живой проверки рядом с игрой снова не было. Порог
`MIN_FIELD_CARS = 4` и правило повтора на живом поле не сверялись — в полевой
журнал пишутся `field_pace` и причины молчания (`repeat_rule`,
`chatter_disabled`, `gap_below_spoken`), первый заезд с `SPOTTER_DIAG=1` покажет.

### Сессия 2026-08-10 — Коуч пилотажа, фаза 4: от наблюдений к уроку

Жалоба пользователя: «коуч — бесполезная функция, ничего не даёт». Тумблер при
этом ВКЛЮЧЁН (`settings.json: driving_coach_enabled: true`), то есть проблема не
в молчании. Три фазы честно работали и говорили верные по отдельности вещи —
«блокируешь переднее левое в седьмом», «в третьем можно позже на тормоз», — а
вместе это набор замечаний, из которого пилот сам должен выбрать, чем заняться.

**Чего не хватало, по пунктам.** Коуч никогда не называл ЦЕНУ: за круг у пилота
десяток неидеальных мест, и без «сколько это стоит» приоритета нет. Не было
ОДНОЙ работы: фазы 1 и 2 говорили каждая про свой поворот. Не было
ПОДТВЕРЖДЕНИЯ: коуч ни разу не сказал «получилось» — а это единственная обратная
связь, ради которой пилот вообще слушает. Дебриф показывал цифры
(консистентность, слабый сектор, счётчик ошибок) без вывода. И ничего не
переживало сессию: каждый заезд начинался с чистого листа.

**Пять новых модулей, ни один не трогает детекторы фаз 1–3.**
`core/coach_ai/cost.py` — цена поворота в миллисекундах за круг и потенциал
круга; `diagnosis.py` — связка цены с причиной; `focus.py` — автомат «одна
работа за раз»; `lesson.py` — вердикт сессии; `TrackHistory` в
`reference_store.py` — эталон и прошлый разбор одним проходом по архиву.

**Нормализация та же, что в `compare.py`, и это не переиспользование ради
красоты.** Тяжёлая машина медленнее в КАЖДОМ повороте; без вычитания медианы
круга «цена» появилась бы у всех поворотов сразу, сумма надулась бы вдвое, а
доля каждого потеряла бы смысл — то есть ровно то, ради чего цена и считается.
Таблица порогов вынесена в `compare.METRICS` публичной: второй копии у коуча
быть не должно, разойдясь, они дали бы «причина есть» в одном модуле и «причины
нет» в соседнем на одних и тех же данных.

**Две разные величины, которые нельзя путать.** ЦЕНА поворота — медиана
превышений по кругам (тренируют привычку, а не один неудачный проезд).
ПОТЕНЦИАЛ круга — время из СВОИХ ЖЕ лучших проездов каждого поворота; эталон в
нём не участвует намеренно: карьерный круг мог быть снят на другой машине, и
потенциал от него обещал бы недостижимое. Вклад одного поворота ограничен двумя
секундами — больше это разворот или сбитый замер, и ограничение показано в
отчёте (`potential_clamped`), а не спрятано.

**Работа меряется по ОКНУ последних кругов, итог — по всей сессии.** Медиана
сессии почти не двигается, когда пилот исправился на десятом круге из двадцати;
коуч, меряющий прогресс по итогу, похвалил бы на финише — когда похвала уже
ничего не стоит. `COACH_FOCUS_WINDOW_LAPS = 6`.

**Поворот без причины работой не становится.** Именно указания вида «здесь ты
теряешь время» и делали коуча бесполезным: применить их нельзя, а раздражают они
сильнее молчания. Такой поворот остаётся в разборе как факт. Срыв бьёт технику
при равной убедительности: сорванное колесо пилот перепроверит на повторе, а
«тормозишь на пятнадцать метров раньше» ему приходится принимать на веру.

**Три реплики на всю жизнь одного фокуса** (`coach.focus_set` / `_progress` /
`_fixed`) плюс пауза в 3 круга между ними — потолок болтливости по построению.
Гистерезис против метаний: чужая проблема забирает работу только будучи в 1,6
раза дороже и не раньше четырёх кругов; фокус, который уже начал получаться, не
отнимается вовсе.

**Здесь величина ЗВУЧИТ — и это не отмена запрета в `coach.ref_*`.** Там
запрещено отклонение («на двенадцать метров раньше»): пилот его в повороте не
применит. Здесь звучит цена («уходит три десятых за круг») — она отвечает не на
«что делать», а на «почему этим стоит заняться». На саму РАЗНИЦУ стоит тест:
упадёт и если цена исчезнет у фокуса, и если величина появится у `ref_*`.
Произношение — `num_to_words.seconds_phrase` («три десятых», «полсекунды»,
«1,2 секунды»).

**Порог события не может быть ниже порога произносимого.** `PROGRESS_MIN_MS`
подняли 80 → 100 (= `MIN_SPOKEN_MS`): подтверждение даётся ровно один раз на
фокус, и непроизносимая величина означала бы, что фокус пометил похвалу выданной,
а пилот не услышал ничего. Молчаливая деградация в единственной обратной связи.
На связь порогов стоит отдельный тест.

**Фаза 2 уступает фокусу, фаза 1 — нет.** Пока в работе один поворот, подсказка
про технику в другом не звучит (`coach_silent: off_focus`) — это то же самое, чем
занят фокус, и вместе они дают шум. Срывы фазы 1 остаются: это реакция на
случившееся, а не второе мнение о том, над чем работать.

**Разбор считается РАЗ В КРУГ и кладётся готовым.** `/api/state` опрашивают
восемь окон оверлея каждые 250 мс — медианы по всей сессии там считать нельзя.
Компактен по построению (три строки потерь + вердикт), поэтому едет целиком, как
«Гараж». Уезжает и в файл заезда (`coach_lesson`): его читает не только экран, но
и следующий визит на трассу.

**Найдено чтением вывода, а не тестом.** Прогон разбора на синтетическом заезде
дал «100% потери — в поворотах 3 и 7»: формально верно, а читается как артефакт
округления — сомнение возникает ровно там, где цифра точна. Теперь «Вся потеря
круга — в поворотах 3 и 7». Все проверки на эту строку до этого проходили.

**UI:** блок «Урок» первым в дебрифе и на всю ширину — лучший круг/потенциал/
запас, куда ушло время (доли полосками), что в работе (было → стало), одна вещь
на следующий раз, прогресс с прошлого визита. Блок отсутствует целиком, пока
данных нет: прочерк читается как поломка.

**Проверено:** полный `pytest` — 4623 теста, 0 падений. По фазе 4 — 91 тест в
пяти новых файлах (`test_coach_cost` 19, `test_coach_diagnosis` 13,
`test_coach_focus` 23, `test_coach_focus_wiring` 17, `test_coach_lesson` 19) плюс
озвучка величины и спеки банка в существующих. `tsc --noEmit`
и production build чистые, `webui/` пересобран (robocopy exit 3). Разбор поднят
на данных НАСТОЯЩЕГО конвейера: синтетический заезд на 14 кругов прогнан через
`CornerHistory`/`diagnose`/`SessionFocus`/`build_lesson`, эфир дал
`set → progress → fixed` по седьмому повороту, вердикт и прогресс прочитаны
глазами.

**Панель браузера в этой сессии не отображалась**, и вкладку выгружало через
доли секунды после загрузки — DOM-проверка живого приложения была недоступна.
Рендер проверен иначе и надёжнее: временная страница `app/lesson-check` с
подставленным разбором прогнана через production build, готовый HTML прочитан с
диска (все элементы блока на месте), страница удалена, `webui/` пересобран
начисто. Приём стоит запомнить — он не зависит от состояния панели вообще.

**Не сделано (осознанно):** `driving_coach_enabled` по-прежнему `False` по
умолчанию — условие прежнее, живая калибровка порогов `slip.py`; у пользователя
он включён вручную. Пороги фазы 4 (`MIN_COST_MS`, `MIN_FOCUS_COST_MS`,
`SWITCH_RATIO`, окно) на живых данных тоже не сверялись — их видно в полевом
журнале (`coach_lesson`, `coach_silent: off_focus`), и первый же заезд с
`SPOTTER_DIAG=1` скажет, надо ли их двигать.

### Сессия 2026-08-10 — Второй экран: он не работал вообще

Первый живой заход с телефона. Жалоба пользователя — «кривой сайт + ничего не
работает» — оказалась не «сыровато», а двумя дефектами, каждый из которых делал
фичу неработающей молча. Прошлая сессия закрыла второй экран на тестах и
десктопной панели, записав честно: «реального захода с телефона не было».

**Гейт резал ПОДРЕСУРСЫ.** Токен ехал двумя путями: один раз в адресе
(`?token=…`) и заголовком `X-Spotter-Token` в fetch-ах. А стили, скрипты и
шрифты браузер запрашивает САМ — ни заголовка, ни query у этих запросов нет.
Замеряно на живом приложении: документ 200, каждый `/_next/static/*` — 401. Тот
же файл с `?token=` — 200. Телефон получал 892 символа голого текста: «кривой
сайт» = без CSS, «ничего не работает» = без JS. Тесты на политику этот класс
дефектов не ловят в принципе — политика была верна, сломана была ПРОВОДКА.

**Кука `spotter_remote_token`** (`HttpOnly`, `SameSite=Strict`, 30 дней, без
`secure` — второй экран живёт по HTTP). Чинит заодно второй дефект:
перезагрузка по «чистому» адресу давала 401, потому что токен вычищается из
адресной строки после загрузки. Права кука не расширяет: `LOCAL_ONLY_PATHS`
(ключи Yandex/GigaChat) остаются локальными и с ней.

**Ловушка Bottle 0.13, стоившая двух неверных реализаций.**
`HTTPResponse.apply()` перезатирает `_headers` и `_cookies` глобального ответа
ЦЕЛИКОМ и вызывается ДВАЖДЫ: в `_handle()` и ещё раз в `_cast()` — то есть уже
после хука `after_request`. `static_file()` возвращает как раз `HTTPResponse`,
поэтому кука, поставленная в `before_request` ИЛИ в `after_request`, молча
исчезает ровно на том ответе, который обязан её принести. Ставить можно только
на сам объект ответа — сделано плагином (`app.install`), он оборачивает маршрут
и работает до первого `apply()`. Плагин, а не пара маршрутов: забытый маршрут
здесь означает страницу, которая грузится один раз и умирает после F5.

**Телефонная вёрстка не существовала.** Замер живого DOM при 375px: сайдбар
`w-60` не сжимается (брейкпоинтов нет), `main` получает 135px, минус `p-6` —
**87 пикселей на контент**, и `overflow-hidden` не даёт отскроллить. На весь UI
споттера — 27 упоминаний брейкпоинтов.

**Решение — отдельный экран, а не респонсив 17 вьюх.** `NewSpotterUI/app/phone/`
→ `webui/phone.html` (тем же способом, что `overlay.html`): позиция и круг,
таймингборд `relative` из `/api/overlay`, шины/износ/топливо/ERS/последний круг,
последняя реплика инженера, 6 последних событий. Новых ручек нет. За рулём не
нужны «Настройки», «Логи» и разметка оверлея — ссылка из панели ведёт на
`/phone.html`, десктопный `/` с телефона по-прежнему открывается.

**Известное ограничение, названное прямо в UI:** `navigator.wakeLock` требует
secure context, по HTTP в LAN недоступен — экран телефона будет гаснуть сам.

**Проверено:** полный `pytest` зелёный; 13 новых тестов ходят настоящими WSGI-
запросами и смотрят на `Set-Cookie` в ответе — тест на чистую функцию ловушку
`apply()` пропускает. Живьём: заход на LAN-адрес с этой же машины даёт
не-loopback `REMOTE_ADDR`, гейт отрабатывает по-настоящему; 19/19 подресурсов
200, перезагрузка без токена 200, при 375px горизонтального выезда нет.
Реального телефона в сети по-прежнему не было — это последнее подтверждение.

и другие типы событий). Пользователь подтвердил: это не регрессия, а второй скрытый баг,
исправленный как побочный эффект первого (эти события по своей природе ВСЕГДА про
игрока). `F1_BENCH`/`F1_SECTOR_BENCH` (`core/engine.py:1857-1866`) имеют идентичный баг
(тот же паттерн `driver=""`, без `vehicle_idx`) — сознательно НЕ исправлено в этой
задаче, отдельный follow-up. См. `docs/superpowers/specs/2026-07-22-racefeed-career-stories-design.md`.
